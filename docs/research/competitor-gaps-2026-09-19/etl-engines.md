# Кандидаты в feature gaps: ETL/data-integration engines

Срез официальных источников на **2026-09-19**. В выборке только движки интеграции/ETL и CDC, а не migration-only продукты: Apache SeaTunnel, Apache Flink CDC, Debezium + Kafka Connect, Conduit, Sling, Alibaba DataX и Apache InLong. Версия указывается там, где она явно есть в источнике.  Все пункты ниже — **кандидаты на gap Transferia**: наличие или отсутствие конкретного поведения в Rust-репозитории должен отдельно установить основной аудит. Формулировка «сигнал» — факт, описанный продуктом; «что проверить» — вывод о возможной функции, а не утверждение о Transferia.

## Приоритеты

* **P0** — влияет на целостность, возобновление или большой initial load; проверять первым.
* **P1** — существенно улучшает эксплуатацию или производительность production ETL.
* **P2** — экосистемная/удобная функция, важная при выборе инструмента, но не блокирующая data-plane корректность.

| 2 **P0** | **Атомарный snapshot→incremental handoff.** Зафиксировать одну позицию журнала, прочитать snapshot и затем продолжить log без пропуска/двойной логической строки. | Flink CDC заявляет distributed historical scan с автоматическим переходом к CDC ([3.5 overview](https://nightlies.apache.org/flink/flink-cdc-docs-release-3.5/)); SeaTunnel описывает snapshot chunks, handoff point и затем binlog/LSN ([CDC architecture](https://seatunnel.apache.org/docs/architecture/cdc-pipeline-architecture/)); Debezium initial snapshot + binlog position ([MySQL connector](https://debezium.io/documentation/reference/stable/connectors/mysql.html)). | Требует connector-specific transaction/log semantics; «at-least-once» сам по себе не означает атомарный handoff. |
| 3 **P0** | **Incremental snapshots параллельно с live stream, с watermark/window dedup.** Snapshot chunk не блокирует CDC, READ отбрасывается при более свежем UPDATE/DELETE. | Debezium incremental snapshot работает chunk-by-chunk, watermark/window и продолжает stream одновременно ([docs](https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-incremental-snapshots)). | Поддержка зависит от конкретного Debezium connector и signaling; snapshot может требовать права на signal table. |
| 4 **P0** | **Возобновление прерванного incremental snapshot с последнего chunk**, а не с начала таблицы; нужен durable progress и idempotent replay. | Debezium прямо обещает resume interrupted incremental snapshot without data loss ([тот же раздел](https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-incremental-snapshots)). | Требуется внешний durable offset/state store; потеря state сводит функцию к повторному полному чтению. |
| 5 **P0** | **Checkpoint восстанавливает split progress и source offset одновременно.** Checkpoint должен включать enumerator, незавершённые splits, log cursor и sink state. | SeaTunnel checkpoint recovery восстанавливает source offsets и sink commit state ([mechanism](https://seatunnel.apache.org/docs/architecture/fault-tolerance/checkpoint-mechanism/)); Flink CDC заявляет exactly-once после job failures ([3.5 home](https://nightlies.apache.org/flink/flink-cdc-docs-release-3.5/)). | Фактический EOS зависит от sink; checkpoint только source не устраняет duplicate side effects. |
| 6 **P0** | **End-to-end exactly-once через sink two-phase commit/idempotent commit.** Перед commit sink готовит transaction, checkpoint связывает source offset и commit, recovery повторяет commit безопасно. | SeaTunnel документирует checkpoint + sink 2PC recovery ([checkpoint mechanism](https://seatunnel.apache.org/docs/architecture/fault-tolerance/checkpoint-mechanism/)); Flink CDC connector matrix перечисляет Exactly-once Read ([overview](https://nightlies.apache.org/flink/flink-cdc-docs-release-3.5/docs/connectors/flink-sources/overview/)); SeaTunnel JDBC пример использует `is_exactly_once` и XA ([schema evolution](https://seatunnel.apache.org/docs/introduction/configuration/schema-evolution/)). | Не всякая комбинация source/sink поддерживает EOS; XA может быть недоступен/дорог. Нужен явный контракт, а не глобальный marketing label. |
| 7 **P0** | **Schema history, привязанная к позиции журнала.** При restart восстановить DDL до binlog/LSN позиции и декодировать старые события правильной схемой. | Debezium хранит DDL в internal schema-history topic и replay-ит его при restart ([MySQL schema history](https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-schema-history)). | Schema history — внутренний Kafka topic с глобальным порядком; Debezium требует один partition. Это не то же самое, что downstream schema evolution. |
| 8 **P0** | **Явная политика schema evolution с fail/allow/lenient и per-event allowlist.** CREATE/ADD/ALTER/RENAME/DROP/TRUNCATE должны иметь observable policy и не терять данные по умолчанию. | Flink CDC 3.5: `exception`, `evolve`, `try_evolve`, `lenient`, `ignore`, плюс include/exclude event types ([schema evolution](https://nightlies.apache.org/flink/flink-cdc-docs-release-3.5/docs/core-concept/schema-evolution/)); SeaTunnel поддерживает ADD/DROP/RENAME/MODIFY для ряда CDC/sinks, выключено по умолчанию ([schema evolution](https://seatunnel.apache.org/docs/introduction/configuration/schema-evolution/)). | Flink `try_evolve` предупреждает о возможной потере при casting; SeaTunnel coverage connector-specific. Для Transferia gap считать только после аудита backend и runtime. |
| 9 **P0** | **Durable, pluggable offset store + controlled reset/replay.** Позиция должна переживать процесс/host restart; оператор должен уметь inspect/reset с предупреждением о duplicate/skip semantics. | Kafka Connect/ Debezium хранят offsets в Kafka и поддерживают альтернативные stores; Debezium перечисляет Kafka/Redis/JDBC/file варианты ([state storage](https://debezium.io/documentation/reference/3.7/configuration/storage.html), [Debezium Server](https://debezium.io/documentation/reference/operations/debezium-server.html)). | Reset offsets — potentially destructive advanced operation; нельзя предлагать silent seek. |
| 10 **P0** | **Distributed workers/tasks с rebalance и restart.** Connector task ownership должна восстанавливаться после worker failure, offsets/config/status — в отдельном durable cluster store. | Debezium tutorial описывает Kafka Connect distributed restart: service поднимает зарегистрированные tasks и resume-ит с прошлого места ([tutorial](https://debezium.io/documentation/reference/stable/tutorial.html#restarting-the-kafka-connect-service)). | Kafka Connect требует Kafka cluster и его internal topics; это тяжёлая инфраструктурная зависимость, не обязательная для локального Rust worker. |
| 11 **P0** | **Ack propagation и backpressure через DAG.** Source commit/ack только после успешной обработки всеми destination; при forceful stop unacked сообщения будут replay. | Conduit pipeline — DAG из source, processors, destinations; order/backpressure и ack/nack semantics описаны в [Pipeline Semantics](https://conduit.io/docs/core-concepts/pipeline-semantics/). | Conduit гарантирует порядок внутри одного source, но не между source; destination plugin может буферизовать и нарушить внешний order. |
| 12 **P0** | **Явный bad-record policy: bounded error count/percentage, DLQ или fail-closed.** Ошибочная запись не должна тихо теряться; лимит должен быть пользовательской конфигурацией. | DataX `TaskPluginCollector` собирает dirty records, job завершается при превышении заданного count/percentage ([plugin guide](https://github.com/alibaba/DataX/blob/master/dataxPluginDev.md)); Conduit поддерживает DLQ/reroute ([semantics](https://conduit.io/docs/core-concepts/pipeline-semantics/)). | DataX допускает percentage tolerance: это сознательная потеря и потому требует очень явного UX/diagnostics. DLQ меняет исходный delivery guarantee. |
| 13 **P0** | **Защищённый snapshot split/CDC key contract.** Перед запуском валидировать nullable/non-indexed split key, gaps, composite keys и duplicate primary-key identity; runtime перепроверять перед commit. | Flink CDC Postgres имеет sampling/uneven chunk fallback и concurrent read options ([Postgres connector](https://nightlies.apache.org/flink/flink-cdc-docs-release-3.5/docs/connectors/flink-sources/postgres-cdc/)); SeaTunnel Postgres аналогично документирует split analysis и fallback ([connector](https://seatunnel.apache.org/docs/connectors/source/PostgreSQL-CDC/)). | «Fallback to one split» безопаснее, но может быть неприемлемо медленным; silent coercion split key — data correctness risk. |
| 14 **P1** | **Source/sink throughput controls с одинаковыми измеримыми units.** Byte/s, rows/s, batch size, channel/reader count, memory/backpressure должны быть ограничиваемыми на job/table. | SeaTunnel CDC example задаёт `read_limit.bytes_per_second`, `read_limit.rows_per_second`, parallelism ([CDC schema-evolution example](https://seatunnel.apache.org/docs/introduction/configuration/schema-evolution/)); DataX speed channel/byte controls видны в official README ([DataX](https://github.com/alibaba/DataX)). | Глобальный rate limit может unfairly throttle маленькие и большие таблицы; нужно документировать scope и burst. |
| 15 **P1** | **Batch sink optimization с transactional boundaries.** Sink должен уметь configurable batch/flush, atomic commit, retry только безопасного batch и раскрывать partial failure. | SeaTunnel sink API выделяет SinkWriter, SinkCommitter, AggregatedCommitter ([sink architecture](https://seatunnel.apache.org/docs/architecture/api-design/sink-architecture/)); InLong DataProxy sink имеет `maxThreads`, pack count/size, queue bound и retry interval ([configuration](https://inlong.apache.org/docs/modules/dataproxy/configuration/)). | Максимальный batch/queue — operational limit, его нельзя hardcode-ить так, чтобы терять данные; large batch ухудшает latency/recovery. |
| 16 **P1** | **Multi-table capture, wildcard selection и stable routing.** Таблицы выбираются pattern-ом, metadata (database/schema/table) маршрутизирует каждую в однозначный physical sink; schema changes изолированы. | SeaTunnel multi-table CDC recipe ([recipe](https://seatunnel.apache.org/docs/getting-started/recipes/multi-table-cdc/)) и placeholders/schema-evolution mapping ([config](https://seatunnel.apache.org/docs/introduction/configuration/schema-evolution/)); Sling streams поддерживают wildcards и per-stream config ([structure](https://docs.slingdata.io/concepts/replication/structure)). | Routing нескольких несовместимых upstream tables в одну sink table опасен; нужно fail-fast на key/schema collision. |
| 17 **P1** | **CDC row-kind materialization.** Insert/update-before/update-after/delete должны сохраняться или явно преобразовываться в upsert/delete/append; primary-key identity — часть sink contract. | SeaTunnel CDC architecture описывает row kinds и sink upsert/delete ([CDC architecture](https://seatunnel.apache.org/docs/architecture/cdc-pipeline-architecture/)); Sling incremental strategy различает PK+update key upsert и append-only ([modes](https://docs.slingdata.io/concepts/replication/modes)). | Append-only target не может silently эмулировать current-row semantics; transformation должна быть explicit. |
| 18 **P1** | **Full-refresh/truncate/incremental/snapshot/backfill как разные режимы.** Каждый режим имеет разные destructive/append semantics, state and validation; default не должен silently drop target data. | Sling перечисляет режимы и temporary-table final load ([modes](https://docs.slingdata.io/concepts/replication/modes)). | Это batch ELT feature Sling, не CDC guarantee; full-refresh destructive, поэтому требует explicit choice/confirmation. |
| 19 **P1** | **Range backfill по update key с chunking и overlap policy.** Оператор может повторно дозагрузить исторический диапазон, с documented dedup/upsert semantics. | Sling backfill mode принимает range по update key ([backfill](https://docs.slingdata.io/examples/database-to-database/backfill)); replication guide показывает date/number `chunk_size` ([official repo guide](https://github.com/slingdata-io/sling-cli/blob/main/cmd/sling/resource/llm_REPLICATION.md)). | Cursor-only incremental (`max(update_key)`) пропускает late updates при неудачном ключе; backfill должен показывать duplicates, а не скрывать их. |
| 20 **P1** | **API/file incremental cursor state.** Для API/file source сохранять opaque cursor/page token/watermark between runs и атомарно обновлять state после sink commit. | Sling API incremental использует `sync` для сохранения state ([example](https://docs.slingdata.io/examples/api-to-database/incremental)); database incremental сохраняет max update key ([modes](https://docs.slingdata.io/concepts/replication/modes)). | API cursors часто не тотальны и могут истечь; обязан быть explicit replay/backfill path. |
| 21 **P1** | **Multiple destinations, fan-out, routing and DLQ in one pipeline.** Record is acked only after all selected destinations or an explicit DLQ route; per-destination failure observable. | Conduit fan-out node waits for downstream destinations and has destination processors/DLQ ([semantics](https://conduit.io/docs/core-concepts/pipeline-semantics/)). | Fan-out multiplies sink side effects and recovery cost; order across destinations need not be globally atomic. |
| 22 **P1** | **Operator lifecycle API: submit, status, stop, cancel, savepoint, restore.** Actions должны быть idempotent, auth-protected, and expose restore source job/checkpoint. | SeaTunnel REST cookbook lists submit/monitor/stop/cancel/savepoint/recovery and `restoreMode=CHECKPOINT` ([REST lifecycle](https://seatunnel.apache.org/docs/engines/zeta/rest-api-job-lifecycle/)). | SeaTunnel Web UI itself currently view-only; lifecycle actions are REST/CLI ([Web UI](https://seatunnel.apache.org/docs/engines/zeta/web-ui/)). Не смешивать UI presence с API capability. |
| 23 **P1** | **DAG/worker/split observability.** UI/API должны показывать job graph, per-source lag, split progress, checkpoint age, throughput, errors, logs and worker health. | SeaTunnel Web UI job detail показывает DAG, metrics, exceptions, config, logs, workers/master resources ([Web UI](https://seatunnel.apache.org/docs/engines/zeta/web-ui/)); Debezium exposes snapshot/streaming/schema-history JMX metrics ([MySQL monitoring](https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-monitoring)). | Metrics names and cardinality must be stable and credential-free; UI snapshot alone не заменяет machine-readable API. |

| 25 **P1** | **Control/data-plane separation and config reconciliation.** Manager distributes versioned source-channel-sink metadata; workers periodically reconcile and expose active config version. | InLong Manager/DataProxy architecture fetches metadata and maps streams to MQ topics ([DataProxy overview](https://inlong.apache.org/docs/1.10.0/modules/dataproxy/overview)); DataProxy auto-syncs config from Manager ([configuration](https://inlong.apache.org/docs/modules/dataproxy/configuration/)). | Dynamic config can race with in-flight records; update needs generation/compatibility barrier. |
| 26 **P1** | **Explicit delivery semantics per source/sink pair.** Document and expose at-most-once, at-least-once, exactly-once/none, including what happens on sink retry and restart. | InLong Kafka load node enumerates `at-least-once`, `exactly-once`, `none` ([Kafka sink](https://inlong.apache.org/docs/data_node/load_node/kafka/)); Conduit documents at-least-once across restart ([semantics](https://conduit.io/docs/core-concepts/pipeline-semantics/)); Debezium supports Kafka Connect exactly-once for eligible source connectors ([EOS](https://debezium.io/documentation/reference/3.4/configuration/eos.html)). | Guarantee is pair-specific and may change with external transaction support; a single global mode flag is misleading. |
| 27 **P1** | **Runtime/ad-hoc snapshot signal with table subset and predicate.** Operator can request incremental or blocking snapshot while connector runs, selecting tables and optional conditions. | Debezium signaling supports `incremental`/`blocking`, table regex/list and `additional-conditions` ([signaling](https://debezium.io/documentation/reference/3.0/configuration/signalling.html), [MySQL](https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-incremental-snapshots)). | Blocking snapshot intentionally pauses stream and can duplicate records; signal permissions and connector support vary. |
| 28 **P1** | **Source-side projection/filter/computed columns with a typed transform contract.** Push down safe predicates/projection; distinguish source query transformation from row-level transform and preserve null/precision. | Flink CDC lists column projection, computed column, filter and scalar functions ([3.5 home](https://nightlies.apache.org/flink/flink-cdc-docs-release-3.5/)); Sling supports select/exclude and transforms ([structure](https://docs.slingdata.io/concepts/replication/structure)); Conduit has processors ([repository overview](https://github.com/ConduitIO/conduit)). | Pushdown changes source load and may affect CDC key/ordering; transformation must be explicit and validated at destination boundary. |
| 29 **P1** | **Connector plugin isolation and typed extension registry.** Add source/sink/transform without coupling core runtime to heavyweight dependencies; discover capability/options and validate before worker start. | DataX loads Reader/Writer plugins from `plugin.json` ([DataX README](https://github.com/alibaba/DataX)); SeaTunnel provides connector listing and option rules ([connector check](https://seatunnel.apache.org/docs/engines/command/connector-check/)); Conduit connectors use gRPC plugins and registry install ([repo](https://github.com/ConduitIO/conduit)). | Plugin isolation can complicate exactly-once state compatibility and versioning; a catalog is not proof of runtime support. |
| 30 **P1** | **Operational retries with bounded backoff and connector-specific transient/permanent classification.** Retry only replay-safe operation; surface attempt count and stop on permanent/schema/data corruption. | InLong SDK documents per-message retries and retry metrics ([Go SDK](https://inlong.apache.org/docs/sdk/dataproxy-sdk/go/)); InLong DataProxy exposes process/reload intervals and queue bounds ([configuration](https://inlong.apache.org/docs/modules/dataproxy/configuration/)); Conduit forceful stop/replay semantics ([semantics](https://conduit.io/docs/core-concepts/pipeline-semantics/)). | Blind retry can duplicate non-idempotent sink writes or hide corruption; backoff must be configurable and observable. |
| 31 **P2** | **Single-node embedded mode plus external scheduler/scale-out seam.** Run a minimal pipeline without JVM/cluster, while allowing fleet control/scheduling and HA above the engine. | Conduit deliberately uses single-node engine; roadmap says distribution is scheduling and active/passive checkpoint reschedule ([architecture/roadmap](https://github.com/ConduitIO/conduit/blob/main/ROADMAP.md)). | Roadmap items are not shipped guarantees; include only as future-facing candidate, not current parity requirement. |

## Наблюдения по продуктам (для взвешивания gap)

### Apache SeaTunnel (Zeta/2.3.x-next)

Это наиболее близкий «универсальный engine» в выборке: split-aware CDC, checkpoint/2PC, schema evolution, REST и большое число source/sink plugins. При этом его Web UI — в основном observability, а lifecycle остаётся REST/CLI; CDC schema evolution поддерживают только перечисленные source/sink и часть событий. В качестве первоисточников следует предпочитать versioned 2.3.13 connector catalogs ([source](https://seatunnel.apache.org/docs/2.3.13/connectors/source/), [sink](https://seatunnel.apache.org/docs/2.3.13/connectors/sink/)) и страницы `Version: Next` только как текущую development signal.

### Apache Flink CDC 3.5.0 и текущая 3.7-SNAPSHOT

Flink CDC имеет сильнейший baseline для initial snapshot + CDC: parallel/incremental snapshots, EOS-after-failure, schema evolution и YAML pipeline. Official 3.5 matrix полезна тем, что явно показывает ограничения по connector: MongoDB/MySQL/Oracle/Postgres/SQL Server/Db2 имеют parallel + EOS + incremental snapshot, а OceanBase/TiDB/Vitess — неполный набор ([matrix](https://nightlies.apache.org/flink/flink-cdc-docs-release-3.5/docs/connectors/flink-sources/overview/)). Не переносить свойства MySQL на весь catalog.

### Debezium + Kafka Connect 3.x

Сильные стороны — schema-history replay, ad-hoc incremental snapshots, source metadata и Connect distributed offset/task lifecycle. Ограничение — Kafka Connect/Kafka являются частью topology; EOS заявлен только для eligible connectors, а incremental snapshot/signal support connector-specific. Debezium Server позволяет заменить Kafka storage, но это отдельный deployment mode ([Debezium Server](https://debezium.io/documentation/reference/operations/debezium-server.html)).

### Conduit (официальный Go engine)

Conduit интересен как компактный Kafka Connect replacement: gRPC connector plugins, DAG fan-out, strict source-order, backpressure, ack/nack и at-least-once restart behavior ([repo](https://github.com/ConduitIO/conduit), [semantics](https://conduit.io/docs/core-concepts/pipeline-semantics/)). Ограничение — single-message-per-node/no explicit buffer и single-node design; сложные distributed snapshots/stateful joins сознательно не являются целью ([roadmap](https://github.com/ConduitIO/conduit/blob/main/ROADMAP.md)).

### Sling (CLI/ELT)

Sling не является CDC engine уровня Debezium: его сильная сторона — повторяемые database/file/cloud replications, modes `full-refresh`, `truncate`, `incremental`, `snapshot`, `backfill`, per-stream PK/update key, hooks, `SLING_THREADS` и state для API/database cursor. Основные ограничения — cursor/update-key модель, а не log-based transaction ordering; EOS и distributed worker protocol в официальных docs не заявлены. Факты — [modes](https://docs.slingdata.io/concepts/replication/modes), [structure](https://docs.slingdata.io/concepts/replication/structure), [incremental API](https://docs.slingdata.io/examples/api-to-database/incremental).

### Alibaba DataX (open-source DataWorks integration engine)

DataX даёт очень ясную модель Job→Task→TaskGroup→Reader/Channel/Writer, split и channel concurrency, speed limits и dirty-record limits ([introduction](https://github.com/alibaba/DataX/blob/master/introduction.md), [plugin guide](https://github.com/alibaba/DataX/blob/master/dataxPluginDev.md)). Это преимущественно standalone/offline batch; коммерческий DataWorks добавляет distributed/real-time/whole-incremental возможности, которые нельзя приписывать открытому DataX. Official README прямо перечисляет open-source scope and commercial distinction ([README](https://github.com/alibaba/DataX)).

### Apache InLong 2.4.x

InLong — full-scenario (ingestion/synchronization/subscription) platform, а не только library: Manager, Agent, DataProxy, Sort, MQ, Dashboard/Audit. Сильные signals — durable disk channel, MQ routing, configurable batching, audit/metrics, source/load node catalogs и operational Dashboard/CLI ([architecture](https://inlong.apache.org/docs/1.10.0/modules/dataproxy/overview), [deployment 2.4](https://inlong.apache.org/docs/deployment/bare_metal/), [README/catalog](https://github.com/apache/inlong)). Ограничение — MQ-centric topology and connector versions; exactly-once appears per load connector, not a universal end-to-end guarantee.

## Как использовать этот документ

1. Основной агент должен пометить каждый ряд `implemented / partial / absent / unknown` после аудита локальных crates, registry, configs and tests; этот файл намеренно не делает таких утверждений.
2. Для P0 требуются startup-validation и runtime/recovery tests: split boundaries, duplicate/late CDC, schema DDL, checkpoint restore, sink commit/replay.
3. Connector shortlist не превращать в «список названий»: приоритет — семантика (snapshot, offset, transaction, schema, delete) и честная version/edition matrix.
4. Для источников `master`, `Next`, `SNAPSHOT` или roadmap пометка означает development signal; release-specific claim делать только по соответствующей stable/versioned странице.

Этот раздел — read-only сверка с текущим Rust-кодом (пути и строки — состояние рабочего дерева на 2026-09-19). Статусы: **partial** означает, что есть близкий механизм, но нет всей конкурентной семантики; **absent** — в проверенных контрактах реализация не обнаружена; **unknown** — нужен отдельный connector/runtime аудит. ### Короткий вывод локального аудита

Наиболее точные кандидаты для сопоставления с конкурентами: (a) remote shared durable CAS/lease + worker membership, (b) elastic reassignment/rescaling поверх фиксированных `total_workers/worker_index`, (c) generic rows/s + bytes/s throttling вместо одного memory/backpressure budget, (d) cross-partition ordered CDC apply barrier, (e) row/column checksum localization + explicit repair, (f) coordinated savepoint/restore and rolling configuration upgrade. При этом текущая реализация уже имеет существенные основания не помечать её как single-threaded: phase runner запускает несколько partition tasks, а внутри каждой partition reader/parser/sink работают как отдельные async tasks; ограничение находится на уровне scheduler/topology semantics и sink actor ordering.
