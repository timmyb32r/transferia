# Как системы переноса данных разбивают таблицы

Исследование по [каталогу конкурентов](competitor-catalog-2026-09-20.md),
20 сентября 2026 года. Предмет исследования — прежде всего разбиение **чтения
одной исходной таблицы** для snapshot/backfill. Параллельная обработка уже
прочитанного потока, файловые splits и партиционирование приёмника учитываются
отдельно.

**Вывод:** единственного лучшего splitter нет. Для Transferia разумны общий
планировщик небольших задач и два явно разных протокола: согласованный batch
snapshot и возобновляемый backfill с CDC. PostgreSQL может использовать физические
диапазоны страниц внутри общего снимка; переносимый путь — индексированные
диапазоны ключа с адаптацией по фактической работе. Hash и OFFSET не стоит делать
универсальным способом ускорения.

## Что именно называют разбиением

| Механизм | Пример | Даёт параллельное чтение одной таблицы? |
|---|---|---|
| Несколько таблиц одновременно | Pool задач initial snapshot | Нет, если на таблицу приходится один reader |
| Несколько SQL-предикатов одной таблицы | `k < b`, `k >= b` | Да, если queries исполняются одновременно |
| Последовательный keyset paging | `k > last ORDER BY k LIMIT n` | Сам по себе нет; ограничивает память и позволяет checkpoints |
| Low/high-watermark chunks | Incremental snapshot + CDC reconciliation | Протокол согласования; параллельность зависит от реализации |
| Физические участки хранения | PostgreSQL CTID pages, Oracle ROWID extents | Да, при поддержке и корректном snapshot-протоколе |
| Нативные партиции/шарды | Секции таблицы, region/tablet, API scan token | Да, но задачи уже заданы структурой источника |
| Разделение после чтения | Hash shuffle в Flink/Spark | Ускоряет downstream, не исходное чтение |
| Файлы и row groups | Parquet, Iceberg manifest, object prefixes | Да для файлового источника; не доказательство SQL splitter |
| Пакеты записи | Bulk INSERT/COPY, target partition | Не определяет параллельность reader |

Размер batch, число workers и число splits — три разных параметра. Возможны
тысяча небольших splits, восемь readers и десятки Arrow batches внутри каждого
split. Жёсткое соответствие «один worker = один кусок до конца» создаёт хвосты
при неравномерных данных.

## Карта практических решений

Подробные версии, пути, условия и ссылки находятся в приложениях. Таблица
объединяет семейства алгоритмов; она не утверждает равные гарантии всех продуктов
в одной строке.

| Семейство | Подтверждённые примеры | Существенная особенность |
|---|---|---|
| Числовой MIN/MAX → равные интервалы значений | DataX, Spark JDBC, Flink JDBC, ConnectorX/Polars, Dask, Sqoop | Равные значения не означают равное число строк |
| Выбор между арифметическими и найденными в данных границами | Flink CDC, InLong, SeaTunnel, RisingWave | Оценка плотности/порций помогает при разреженных ключах |
| Квантили и histogram | Transferia Go PostgreSQL, Daft, Gobblin Salesforce, PeerDB QRep NTILE | Баланс лучше, планирование может быть дорогим |
| Hash/modulo на стороне SQL | Transferia Go, Ray Data, ChunJun; AWS Glue, HVR | Ровная маршрутизация может стоить нескольких полных сканов |
| Физические диапазоны | DuckDB PostgreSQL extension, pgcopydb, pgstream, PeerDB, Feldera/ETL, архивный pg_flo; Fivetran, Artie | Не нужен числовой PK; критичны snapshot и идентичность relation |
| Oracle ROWID/extents | Transferia Go; Google Datastream использует ROWID | Знание хранения уменьшает стоимость логического планирования |
| Нативные partitions/regions | Transferia Go MySQL, mydumper, Dumpling/TiDB; AWS DMS, Qlik | Естественное pruning; крупную партицию иногда надо делить дальше |
| Адаптация размера следующего куска | mydumper, MySQL Shell; отдельные source-available readers | Обратная связь по времени/объёму лучше одного размера на всю таблицу |
| Keyset + watermark | Debezium incremental snapshot, Flink CDC; Estuary | Решает согласование с изменениями; не тождественно global point-in-time |
| Пользовательские SQL subsets | DataX querySql, NiFi, Hazelcast; GoldenGate, Syniti | Гибко, но полноту и непересечение условий нужно обосновывать |
| Серверное chunking/API | Gobblin Salesforce PKChunking, native shard/token sources | Лучший доступ к знаниям источника; менее переносимо |
| OFFSET/номер строки | NiFi, некоторые JDBC paging readers | Дорого на поздних страницах; на меняющихся данных нужны дополнительные гарантии |

Важные различия, которые легко пропустить:

- **Debezium:** incremental chunks и initial snapshot thread pool — не одно и
  то же. Наличие обоих не доказывает параллельный snapshot одной таблицы.
- **Sling:** открытый код содержит интерфейс chunking, но проверенные функции
  возвращают ошибку с требованием другой поставки. Реальные chunking-возможности
  описаны для Pro/Platform. Нельзя приписать их OSS-сборке по именам параметров.
- **Transferia Go и управляемый Yandex Data Transfer:** отдельные продукты и
  поверхности настройки; найденные в Go стратегии не доказывают доступность
  соответствующего режима в облаке.
- **Spark JDBC и Flink JDBC:** одинаковые слова lower/upper bound не гарантируют
  одинаковую семантику. В проверенном Spark bounds задают stride с открытыми
  внешними хвостами; в проверенном Flink JDBC range попадает в предикат чтения.
- **Коммерческие range-режимы:** документированные ограничения AWS DMS/Qlik
  по NULL делают выбранный ключ частью корректности, а не только настройки
  скорости. Конкретные режимы и версии разобраны в коммерческом приложении.
- **Estuary, Pathway, текущие ingestr и Pentaho:** наличие доступного кода не
  отменяет проверки текущей лицензии. Исторические OSS-версии и текущие
  source-available версии нельзя смешивать.

## Эффективность: откуда берётся ускорение и где оно исчезает

Обозначения: `N` — число строк, `B` — прочитанные байты, `P` — readers,
`C` — число chunks, `M` — строки в одном chunk. Оценки предполагают обычный
row-store; реальный план, cache, MVCC и индекс могут изменить стоимость.

| Стратегия | Планирование и совокупное чтение | Сильные стороны | Слабые стороны |
|---|---|---|---|
| Равные диапазоны MIN/MAX | Bounds дёшевы при подходящем индексе; без него уже возможен полный проход. Затем суммарно примерно `N` строк индексных диапазонов | Простота; мало round trips; хорошо для плотного возрастающего ID | Skew, большие пробелы, корреляция ширины строк с ключом; unordered heap fetch может проиграть sequential scan |
| Точные квантили / NTILE | Просмотр ключей, иногда сортировка `O(N log N)`; даже индексный порядок не делает чтение всех ключей бесплатным | Почти равные строки; полезно для сильного skew | Дорогой старт; не равные байты/время; повторяющиеся границы требуют обработки |
| Приближённые квантили/статистика | Выборка или системная статистика; затем обычные ranges | Быстрый старт, умеренная цена | Ошибки и устаревание оценок; статистика не должна определять полноту покрытия |
| Keyset seek | Около `N` прочитанных строк + `C` поисков границы при индексе; отдельный проход только по ключам может добавить работу | Строки/UUID/composite PK без арифметики; дешёвое возобновление внутри того же снимка | Один курсор последовательный; нужна отдельная стратегия seed ranges для нескольких readers |
| Hash/modulo SQL | Если нет pruning/подходящего индекса — вплоть до `P × N` проверок строк и вычислений hash | Не чувствителен к пробелам numeric ID; часто ровные количества | Нагрузка на CPU/I/O источника; NULL; modulo крайних signed значений; hash не гарантирует равные байты |
| OFFSET страницы | При `C` страницах порядка `N(C+1)/2` просмотренных позиций, если каждая начинает проход заново | Простой интерфейс | Суммарная работа растёт с количеством страниц; expensive sort; нестабильность без snapshot/order |
| CTID/ROWID blocks | План по метаданным страниц/extent либо дополнительный запрос границ; примерно один основной физический проход при соответствующем access path | Быстрый full dump, нет зависимости от формы PK | DB-specific; bloat/TOAST создают skew; адрес нельзя считать постоянным row ID |
| Нативные shards/partitions | Метаданные, затем pruning/локальное чтение | Использует размещение и серверный parallelism | Число и размеры shards заданы источником; одна горячая shard может ограничивать всё |
| Один scan → несколько downstream workers | Один проход `N`, дальше partition/shuffle | Бережно к источнику; полезно при дорогом parsing/encoding | Сам reader остаётся bottleneck; это не параллельная экстракция |

**Иллюстрация, не результат замера.** Для `N = 100 млн` и восьми одинаковых
OFFSET-частей при проходе от начала получается примерно `450 млн` просмотренных
позиций. Восемь независимых hash full scans могут проверять до `800 млн` строк.
Восемь непересекающихся индексных/физических диапазонов читают нужные строки
примерно по одному разу, хотя I/O страниц и index/heap access могут добавить
существенный overhead. Общий buffer cache уменьшает дисковое чтение, но не
обязательно SQL CPU и memory bandwidth.

Время выполнения снизу ограничено самым медленным ресурсом:

`T >= max(B_source / source_bandwidth, B_wire / network_bandwidth, sink_work / sink_rate,
         max(chunk_work / worker_rate))`.

Здесь `B_source` — фактическая работа чтения источника в байтах, а `B_wire` —
переданный объём после projection/encoding/compression. Это разные величины:
index/heap overread не обязан уходить в сеть.

Следовательно, увеличение `P` помогает только до насыщения источника, сети или
приёмника. Нужны ограничения connections/I/O, bounded queues и обратная связь
от sink. Простой benchmark «P=16 быстрее P=1» без source CPU, bytes scanned и
нагрузки на рабочие запросы недостаточен.

Даже физические splitter различаются ценой планирования: проверенный pgstream
использует `MAX(ctid)`, который может потребовать дополнительного прохода;
Feldera/ETL использует размер relation и открытые внешние границы. Использовать
устаревший `relpages` как точное покрытие опасно: в архивном pg_flo найден путь,
где нулевая оценка создаёт ноль задач. Это замечание по исходникам, не
воспроизведённый нами runtime-дефект. См. [дополнительный аудит](research/table-splitting-2026-09-20/ADDITIONAL-CODE.md).

### На каких данных меняется победитель

| Данные/условия | Что обычно имеет смысл проверить первым |
|---|---|
| Плотный индексированный bigint, узкие строки | Простые ranges; они могут быть быстрее сложного adaptive planner |
| Разреженный ID, Zipf-skew, удалённые диапазоны | Статистические seed boundaries + небольшие адаптивные keyset chunks |
| UUID или composite PK | Server-side ordered keyset/tuple ranges; без арифметики над текстовым представлением |
| Полный dump PostgreSQL, широкий heap, слабая корреляция PK/heap | CTID page ranges под общим snapshot против sequential COPY baseline |
| Много TOAST/LOB, неодинаковая ширина | Адаптация по фактическим bytes/time, не только row count |
| Очень медленный sink | Уменьшить readers/backpressure; extra splits сами по себе не ускорят |
| Длительная загрузка изменяемой БД | Watermark backfill + CDC, если требуемая семантика допускает convergence вместо одного общего снимка |
| Таблица без PK | Согласованный физический/однопроходный batch; CDC updates/deletes требуют отдельного подтверждённого identity contract |

Это приоритеты экспериментов, а не заранее гарантированный рейтинг продуктов.

## Корректность разбиения

Для выбранного снимка `S` и исходного множества строк `R(S)` план должен задавать
задачи `R_i(S)` с двумя свойствами:

`union(R_i(S)) = R(S)` и `R_i(S) ∩ R_j(S) = ∅` при `i != j`.

Здесь элементы — экземпляры/версии строк, а не только их значения. Две
одинаковые keyless строки должны сохраниться дважды; сравнение значений в таком
случае выполняется как multiset, не как обычное множество.

Непересекающиеся предикаты на **разных** снимках не доказывают это равенство.
Строка с изменяемым split key может переместиться между ещё не прочитанной и уже
прочитанной частью. Retry на новом snapshot — тоже другое множество строк.

Нужно различать физическую версию строки, логическую PK-идентичность, событие
CDC и попытку доставки. Hash пригоден для назначения задачи, но не заменяет
полный PK при проверке равенства. Подозрительные повторные snapshot rows с одним
PK должны приводить к ошибке; правило «последний победил» скрыло бы дефект плана.
Предусмотренное протоколом согласование snapshot с журналом — другая операция,
с собственными явно заданными правилами.

Пограничные случаи, обязательные для любого алгоритма:

- **NULL:** обычное сравнение не покрывает его; отдельный доказуемый маршрут или
  отказ от nullable split key. Для composite tuple количество nullable случаев
  и порядок должны быть определены явно.
- **Хвосты:** статистические MIN/MAX не являются фильтром области данных.
  У плана должны быть корректные открытые внешние границы либо доказанная
  точная область того же снимка. Не вычислять `max + 1` с риском overflow.
- **Неуникальный split key:** равные значения нельзя произвольно разделить
  курсором без tie-breaker. Использовать полный уникальный tuple или оставлять
  всю группу в одной задаче с bounded streaming.
- **Типы и порядок:** collation, decimals, UUID, timezone и encoding определяет
  исходная БД. Нельзя округлять или переводить большой integer через float для
  расчёта границ; сравнение сериализованных bytes не всегда совпадает с SQL.
- **DDL и relation identity:** detach/attach partitions, TRUNCATE, rewrite и
  смена схемы должны блокироваться допустимым протоколом либо обнаруживаться до
  публикации некорректного результата.
- **Сбой после записи до checkpoint:** replay разрешён только при доказанной
  idempotency/atomic commit схеме. Отдельная запись checkpoint не превращает
  произвольный append sink в exactly-once.

PostgreSQL прямо описывает CTID как адрес **версии** строки, меняющийся при
UPDATE или перемещении; использовать его как долгоживущую логическую
идентичность нельзя. Это не мешает применять адресные диапазоны внутри
защищённого снимка. [PostgreSQL: system columns](https://www.postgresql.org/docs/current/ddl-system-columns.html).

## Предлагаемый дизайн для Transferia

Это **предложение**, не уже реализованная функция и не доказанный экспериментами
«идеальный» алгоритм. Общая идея — выбирать access path под источник, сохраняя
одни контракты полноты, commit и backpressure.

### A. Согласованный параллельный batch

Подходит для одной точной копии состояния БД и bootstrap через согласованный
replication-slot snapshot.

1. Discovery проверяет тип relation, схему, идентичность, split capabilities и
   ограничения sink. Пользователь явно задаёт семантику снимка и ресурсный бюджет.
2. Координатор создаёт snapshot epoch, удерживает необходимые транзакции/locks
   и фиксирует набор физических relations. Readers импортируют тот же snapshot
   до чтения. Статистические оценки только помогают выбрать размер задач.
3. Сначала учитываются нативные partitions. Для каждой relation выбирается
   проверенный access path: physical page ranges для подходящего PostgreSQL
   heap; иначе индексированные key ranges; иначе корректный single scan.
   Выбранная стратегия видна в плане. Если пользователь потребовал конкретную
   неподдерживаемую стратегию, discovery возвращает ошибку, а не меняет её молча.
4. План создаёт больше небольших задач, чем активных readers. Workers берут их
   из общей очереди, размер следующих задач корректируется по bytes/time.
   Tail splitting делит только невыданную работу либо явно оставшийся диапазон
   после durable boundary; конкурентного владения одним диапазоном нет.
5. Chunk результат и progress коммитятся через поддерживаемый sink-протокол.
   Reader lease имеет generation/fencing. Отозванный worker не может выполнять
   новые sink side effects или commit, а не только отмечать задачу завершённой.
   Если sink не умеет проверять fencing, запись проходит через единственного
   владельца commit/staging; один lease в памяти coordinator недостаточен.
6. После подтверждения всех задач закрывается snapshot. Если owner потерян и
   новый reader уже не может импортировать тот же snapshot, попытка этого epoch
   прерывается явно. Продолжение оставшихся задач на новом snapshot запрещено.

В PostgreSQL snapshot можно импортировать лишь пока экспортирующая транзакция
остаётся открытой. Сохранённая строка snapshot ID не является durable backup.
[PostgreSQL: snapshot synchronization](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-SNAPSHOT-SYNCHRONIZATION).

**Физический PostgreSQL-путь.** Каждая задача адресует отдельную leaf relation
через `ONLY` и полуоткрытый интервал CTID-страниц. Верхняя граница берётся из
безопасно определённой фактической области relation при установленном протоколе,
а не из потенциально устаревшего `pg_class.relpages`. Все строки snapshot должны
быть покрыты, включая крайний блок. Проверяются server version/access method и
реальный план: предикат CTID бесполезен для ускорения, если БД всё равно делает
полный scan на каждую задачу. Partitioned root не читается дополнительно к leaf
tables. Large objects/TOAST учитываются в оценке работы, а не превращаются
автоматически в равные по времени страницы.

Преимущество: дешёвое планирование полного dump, работа без numeric PK.
Цена: удержание MVCC, ограничения DDL, DB-specific реализация; потеря snapshot
может потребовать нового полного epoch. Для любого sink нужен staging и
атомарная публикация/замена epoch либо иной подтверждённый reconciliation,
который не оставляет смесь попыток. Это касается и PK upsert: строка старой
попытки, удалённая к моменту нового snapshot, сама не исчезнет от повторных
upserts. Нельзя обещать безопасный restart поверх уже записанных строк без
контракта удаления старого epoch и публикации нового.

### B. Переносимые адаптивные диапазоны ключа

Это альтернативный access path внутри протокола A и основа chunk selection в C.
Подходит для индексированного уникального порядка, включая composite key.

Начальные seed boundaries берутся из безопасных подсказок статистики или
ограниченной выборки. Они лишь режут **полное** пространство ключей; точность
оценки влияет на баланс, а не полноту. При недоступности подсказок возможен
последовательный генератор keyset-границ. Он не должен притворяться мгновенно
параллельным: стоимость и отставание planner измеряются отдельно.

Внутри seed range worker читает по полному tuple:

```sql
-- Схема запроса; типы параметров, collation и quoting задаёт connector.
SELECT <columns>
FROM <table>
WHERE (<pk1>, <pk2>) > (<last1>, <last2>)
  AND (<pk1>, <pk2>) < (<upper1>, <upper2>)
ORDER BY <pk1>, <pk2>
LIMIT <configured_rows>;
```

Первая страница использует включённую нижнюю границу; `last` появляется только
после фактически прочитанной/подтверждённой строки. Внешний range может не иметь
нижней или верхней границы. Пример предполагает non-null tuple с поддерживаемым
БД порядком; это не универсальный SQL для nullable composite ключей.

При переходе от `last` к следующей странице checkpoint хранит точные типизированные
значения. Никакой «прибавить единицу», преобразования в float или строковой
нормализации. Для задания фиксированной верхней границы следующего chunk можно
прочитать только индексные ключи; это дополнительный проход, и его стоимость
сравнивается с выгодой concurrency. Альтернатива — читать маленькие страницы
внутри уже независимых seed ranges без двойного чтения всех ключей.

Размер следующей порции рассчитывается по сглаженной оценке bytes/row и времени,
в пределах явно настроенных пользователем бюджета памяти, целевого времени
задачи, числа connections и разрешённой нагрузки на источник. Одновременное
использование row/byte/time оценок — оптимизация, не разрешение обрезать большую
строку. Строка, не помещающаяся в допустимый поддерживаемый контракт, вызывает
явную ошибку до side effect; silent truncation недопустим.

**Плюсы:** переносимость, эффективный seek, точные resume boundaries, skew
уменьшается за счёт очереди. **Минусы:** нужен подходящий индекс; key-only
planning может стать bottleneck; широкий/random heap иногда лучше читать
физически. Статические равные интервалы оставляем как простой измеряемый baseline.

### C. Возобновляемый backfill с CDC и watermark

Для длительного initial load или повторной загрузки части живой таблицы, когда
важно продолжать доставлять изменения. Это отдельная семантика: результат
сходится к состоянию журнала, но chunks не образуют один общий point-in-time
snapshot всей БД.

Основа — опубликованный DBLog-подход: ограниченные SELECT chunks согласуются
с потоком изменений через watermark windows, прогресс можно сохранять и
возобновлять. [DBLog paper](https://arxiv.org/abs/2010.12597).

В свежей работе автора DBLog (версия 5 от 9 сентября 2026) формализован
**virtual cut**: при выполнении условий модели replay восстанавливает состояние
на определённой позиции журнала без единого физического snapshot. Описаны
сертификат выполнения и механизированное доказательство Isabelle/HOL. Это
полезная основа для будущей спецификации: отсутствие общего физического снимка
не означает невозможность snapshot-equivalent результата после replay.
Доказательство модели не является доказательством нашей предлагаемой реализации
или любого коннектора. [A Theoretical Study of DBLog](https://arxiv.org/abs/2605.31475v5).

Предлагаемый протокол расширяет эту идею требованиями Transferia:

1. До backfill запустить подтверждённый CDC stream и проверить retention,
   schema/identity и возможность однозначно наблюдать watermark markers в
   порядке журнала. Произвольные два вызова «текущий LSN» этому не эквивалентны.
   Зафиксировать конечный горизонт backfill: верхний tuple/набор seed ranges
   вместе с доказанным критерием завершения. Новые и перемещённые за горизонт
   ключи покрывает CDC; scanner не должен бесконечно догонять новые INSERT.
2. Для bounded chunk зафиксировать low watermark до начала снимка SELECT,
   выполнить SELECT и зафиксировать high watermark после завершения чтения.
   Low marker должен быть committed и наблюдаем по протоколу до SELECT;
   транзакция со старым снимком, открытая до low, не подходит. Дождаться обоих
   markers в CDC с учётом commit-order и семантики
   конкретной БД. Snapshot rows пока находятся в bounded buffer/durable staging.
3. Изменения между markers согласовать по **полному** PK: не публиковать устаревшую
   snapshot-версию ключа, изменившегося в окне. CDC UPDATE/DELETE/PK-change должны
   оставаться корректными; old/new keys учитываются явно. Snapshot-дубликаты
   одного PK — ошибка, а не повод выбрать победителя.
4. Публиковать оставшиеся chunk rows в определённой точке порядка относительно
   CDC, чтобы событие после high watermark не было перезаписано старой строкой.
   Завершение chunk и CDC progress проходит через durability barrier приёмника.
5. Сохранять chunk bounds, watermark state, committed progress и fencing.
   После crash незавершённое окно восстанавливается из достаточного журнала
   либо перечитывается через новый корректный window-протокол. При утрате
   нужного журнала — явная ошибка и новый backfill, без тихого пропуска.

До snapshot конкретного ключа CDC уже может принести UPDATE без полной базы.
Поэтому кроме PK нужен полный after-image либо явно реализованный протокол
восстановления отсутствующих полей. Partial UPDATE и unchanged TOAST нельзя
трактовать как NULL или как уже восстановленную строку. Это проверяется в
контракте source/sink до включения interleaved backfill.

Сначала имеет смысл доказать последовательные окна. Параллельные окна —
отдельный этап: единый log reader, индекс активных окон, ограниченная память и
строгий порядок публикации. Количество строк, попавших в окна, зависит от
`change_rate × window_duration`; увеличение parallelism может раздувать
reconciliation state. Изменение split key не позволяет фильтровать CDC только
по текущему диапазону: старый ключ, новый ключ и уже завершённые chunks тоже
влияют на корректность.

Для keyless таблиц не объявлять CTID универсальной заменой PK в этом протоколе.
Если источник/приёмник не дают доказанную идентичность, поддержать только
подходящий batch-режим или отклонить неподдерживаемую CDC-конфигурацию.
Глобальный транзакционный порядок и атомарность межтабличных транзакций —
отдельные обещания; их нельзя вывести лишь из корректности одного chunk.

**Плюсы:** нет одного многодневного MVCC snapshot, пригоден для resumable
backfill и малой задержки CDC. **Минусы:** существенно сложнее planner; требует
retention, identity, durable state, корректной маршрутизации изменений и
поддержки sink. Это не просто «добавить N запросов».

### Что не стоит включать в автоматический default

- Hash/modulo full scans ради формальной параллельности. Такой режим может быть
  полезен при конкретном индексе/плане или явном выборе пользователя, но сначала
  нужны source-cost measurements и корректная NULL/type семантика.
- OFFSET как основной способ резать большие живые таблицы.
- Точные percentiles всей таблицы перед каждым запуском без измеримой выгоды.
- Resume CTID на новом snapshot как будто это постоянная позиция строки.
- Автоматический переход к более слабой consistency при сбое.
- Автоматическая дедупликация snapshot rows, замена PK хешем, обрезание границ
  или игнорирование неподдерживаемого значения.

## Как это ложится на текущий Transferia Rust

Проверенный PostgreSQL batch reader импортирует `ExportedSnapshot`, строит один
`SELECT ... FROM schema.table` и запускает `COPY` без range predicate.
`source/connector.rs` адресует таблицы по partition index. Следовательно,
наблюдаемая точка расширения — несколько согласованных scan tasks на таблицу,
а не создание ещё одного независимого MVCC snapshot для каждого worker.
См. [reader.rs](../crates/transferia-connector-postgres/src/connectors/postgres/src_batch/reader.rs),
[snapshot.rs](../crates/transferia-connector-postgres/src/connectors/postgres/src_batch/snapshot.rs)
и [connector.rs](../crates/transferia-connector-postgres/src/connectors/postgres/source/connector.rs).
Это вывод по текущему локальному коду, не повторная проверка старого бенчмарка.

Разделение ответственности предлагаемое, а не реализованное:

| Владелец | Контракт |
|---|---|
| Connector | Проверка capabilities, SQL/physical bounds, snapshot/CDC lifetime, server-side ordering |
| Core / нейтральные execution contracts | Идентичность scan task, типизированные границы/opaque connector token, completion и ошибки; без PostgreSQL CTID в общем API |
| Delivery preparation | Полный validated plan до подготовки sink: режим, ресурсные ограничения, совместимость source/sink guarantees |
| Delivery execution/runtime | Очередь задач, leases/fencing, запуск и retry, bounded concurrency |
| Pipeline/sink | Проверка данных, commit barrier, replay/idempotency, подтверждение progress после durability |

Детали размещения новых типов нужно согласовать с существующими core/registry
портами при реализации. Не добавлять несколько почти одинаковых planner API
ради каждого коннектора. Не называть текущий MVCC bootstrap `src_dblog`:
это имя применимо только к фактическому watermark-протоколу C.

Рекомендуемый порядок работ: **A для PostgreSQL → B как альтернативный
индексный путь и переносимая основа → C отдельным проектом**. Сначала получить
проверяемое ускорение snapshot при сохранении нынешних гарантий; затем решать
другую задачу долгого resumable backfill.

## Проверка предложений: программа будущего бенчмарка

В этом исследовании она **не выполнялась**. Для выбора implementation default
нужно сравнить single COPY, static PK range, adaptive keyset, CTID и допустимые
конкурентные реализации на одном ресурсе источника и приёмника.

| Измерение | Набор сценариев |
|---|---|
| Данные | Dense/sparse bigint, UUID, composite/string collation, nullable split field, non-unique field, keyless heap, native partitions |
| Распределение | Равномерное, горячий диапазон, крупные пробелы, разные размеры строк, TOAST/LOB, bloat |
| Параллелизм | 1/2/4/8 readers с одинаковыми ресурсными пределами; отдельный прогон с server-side parallelism под контролем |
| Нагрузка | Quiescent и concurrent INSERT/UPDATE/DELETE, включая смену PK/split key и долгие транзакции |
| Сбои | Reader crash; coordinator/snapshot loss; sink commit без checkpoint; lease expiration; WAL retention loss; DDL/rewrite |
| Скорость | Planning/startup, rows/s, bytes/s, total time, p50/p95/max chunk duration, tail time |
| Цена | Source CPU, physical/logical reads, temp bytes, active sessions, OLTP latency, network, sink throughput, peak memory |
| Корректность | Точное сравнение row multisets для одного snapshot; для CDC — состояние после drain до заданного барьера и проверка порядка/транзакций согласно обещанному контракту |

Count и hash удобны для быстрой диагностики, но совпадение одного хеша не
доказывает равенство данных. Для проверки потерь/дубликатов нужен независимый
точный oracle по поддерживаемой идентичности либо полное сравнение multiset для
keyless batch. Fingerprints не должны скрывать различия типов или точности.

Кандидат принимается, только если улучшение полного времени не куплено
незаметным ослаблением semantics, неограниченной памятью или неприемлемой
нагрузкой на источник. Стабильный single scan остаётся важным baseline:
на некоторых таблицах он закономерно окажется лучшим.
