# Empty Sink Provider

## Компоненты и связи

`EmptySink` — это провайдер-приемник, который считает строки и байты, но никуда не пишет данные. Он имплементирует trait `Sink` (метод `write`) и управляется через `EmptySinkProvider`, который реализует `SinkProvider`. Подключается через общий `ProviderRegistry` по ключу `"empty"`. В пайплайне сидит на месте Writer-а: получает `TableWrite` (набор Arrow-батчей), атомарно инкрементирует счетчики и сразу возвращает `Ok(())`. Никаких сетевых вызовов, никакого I/O — чисто CPU-учет.

## Ключевые решения

- **AtomicU64 с Relaxed ordering** — потому что счетчики нужны только для бенчмарков (приблизительные цифры), и строгая синхронизация между потоками не требуется. Relaxed дешевле на ARM64.
- **Метод reset()** — чтобы можно было делать несколько замеров подряд без пересоздания sink-а. Счетчики обнуляются атомарно.
- **Provider считает байты через get_buffer_memory_size()** — это дает оценку реального размера данных в Arrow-буферах, а не логический размер (полезно для измерения throughput в bytes/sec).
- **create_tables / verify_tables — no-ops с info-логом** — empty-приемнику не нужны таблицы, но контракт `SinkProvider` требует эти методы. Логируем и пропускаем, чтобы пайплайн не падал.

## Трейдоффы

| Решение | Выигрыш | Проигрыш |
|---------|---------|----------|
| AtomicU64 Relaxed | Минимальный оверхед на инкремент | Возможен drift на несколько операций между потоками |
| Подсчет байт через get_buffer_memory_size | Отражает реальный memory pressure | Не учитывает сжатие/формат, который был бы при реальной записи |
| Один Arc<EmptySink> на провайдер | Все воркеры пишут в одни счетчики — глобальная картина | Нет per-partition статистики |
| Box::pin в write() | Совместимость с контрактом Sink (BoxFuture) | Одно лишнее heap-alloc на вызов |

## Corner cases

- **Пустой TableWrite (0 rows)**: write() отрабатывает корректно — счетчики не меняются, Ok возвращается мгновенно.
- **Множественные batchers в TableWrite**: каждый батч обсчитывается отдельно, сумма агрегируется правильно.
- **Одновременный write из нескольких партиций**: AtomicU64 гарантирует корректную сумму без гонок данных (хоть и Relaxed).
- **reset() между замерами**: счетчики обнуляются атомарно, но между reset() и следующим read() может пройти время — для точных бенчмарков лучше делать snapshot (rows_written_before, rows_written_after).
