# Candidate ETL/data-integration feature gaps (research snapshot: 2026-09-19)

This is a competitor-capability report, not an audit of Transferia. Each item is a **candidate gap to investigate**; it does not claim that Transferia lacks the capability. The parent task is auditing the current Rust code separately. “Supported” below means the linked official documentation describes the behavior; it is not a recommendation that the behavior should be copied unchanged.

## Scope and source notes

The comparison covers Apache NiFi, Estuary Flow, Redpanda Connect (the current successor naming for Benthos), Bento, Apache Hop, Meltano, and dlt. These are ETL/data-integration or stream-processing products, rather than database migration tools. Documentation was checked on 2026-09-19. Observed documentation/version labels include: NiFi component documentation 2.12.0; Apache Hop User Manual 2.19.0; dlt documentation 1.30.0; Redpanda Connect pages label both Cloud and Self-Managed where applicable. Estuary’s docs describe the hosted Flow/catalog model. Meltano’s current docs describe the CLI plus external orchestrator model. Bento docs describe the open stream runtime and its `streams` API. Versions and editions can change; the URLs below are the source of truth.

The report intentionally separates (a) behavior worth considering from (b) connector breadth. A feature should be specified in terms of semantics, failure behavior, state, and observability before deciding whether to implement it.

The candidate list also deliberately does not treat ordinary SQL execution, filters, renames, append/merge behavior, parser DLQs, schema-registry decoding, or throughput/autotuning as inherently missing. The higher-value hypotheses are shared-read DAG semantics, cross-batch state, explicit contracts, replay/checkpoint guarantees, and operational control around those primitives. A system can already produce multiple source×sink delivery combinations while still lacking one source read feeding coordinated branches; “fan-out” here means the latter.

## Prioritized candidate feature gaps

Priority is a product hypothesis: P0 is a broadly reusable data-plane/orchestration primitive; P1 is a high-value workflow or operational primitive; P2 is a differentiator or convenience feature. It is not a statement about current implementation status.

### Graphs, fan-out, routing, and enrichment

1. **P0 — First-class named DAGs with dependency-aware execution.** Represent a flow as named tasks/edges rather than only a linear source-to-sink path; validate cycles and expose dependencies, status, retries, and run history per node. Apache Hop distinguishes pipelines (parallel transforms) from sequential workflows/actions, while Estuary’s catalog explicitly composes captures, collections, derivations, and materializations into a graph ([Hop concepts](https://hop.apache.org/manual/next/getting-started/hop-concepts.html), [Estuary catalog](https://docs.estuary.dev/concepts/catalogs/)). Limitation: Hop’s pipeline transforms run in parallel by default, so ordering requires a workflow boundary; Estuary tasks are continuous rather than a batch scheduler.

2. **P0 — Explicit fan-out/fan-in and multi-sink routing.** Allow one input record or batch to be sent to several branches/sinks, with an explicit policy for whether branches are independent, all must succeed, or partial success is acknowledged. NiFi exposes relationship-based routing and load distribution; Redpanda’s `switch` can execute multiple matching cases with `continue`; Bento workflows execute named branches in parallel where possible ([NiFi getting started](https://nifi.apache.org/nifi-docs/getting-started.html), [Redpanda switch](https://docs.redpanda.com/connect/components/processors/switch/), [Bento workflow](https://warpstreamlabs.github.io/bento/docs/components/processors/workflow/)). Limitation: Redpanda warns that switch processing can lose grouping/splitting and does not guarantee case-processing order.

3. **P0 — Declarative content/attribute routing with an explicit unmatched/error path.** Provide a typed predicate language over payload, metadata, headers, and schema; require a visible default route or fail closed when no route matches. NiFi has `RouteOnAttribute` and `RouteOnContent`; Redpanda and Bento offer switch processors ([NiFi getting started](https://nifi.apache.org/nifi-docs/getting-started.html), [Redpanda switch](https://docs.redpanda.com/connect/components/processors/switch/), [Bento switch/error handling overview](https://warpstreamlabs.github.io/bento/docs/components/processors/about/)). Limitation: Bento’s global strict error strategy is incompatible with several local error-handling processors, so the contract must define precedence.

4. **P1 — Parallel enrichment branches with request/result mapping.** Provide an enrichment primitive that derives a request from the original record, calls a database/cache/API, and merges the response back without replacing or losing the source record. Bento’s `branch` explicitly defines `request_map`, child processors, and `result_map`; its `workflow` composes such branches into ordered parallel tiers ([Bento branch](https://warpstreamlabs.github.io/bento/docs/components/processors/branch/), [Bento workflow](https://warpstreamlabs.github.io/bento/docs/components/processors/workflow/)). Limitation: branch-added metadata is not copied automatically; mappings must state what is retained.

5. **P1 — Stateful keyed joins across collections/streams.** Support a continuously maintained join keyed by one or more fields, with deterministic update/delete semantics, state recovery, and explicit handling of unmatched records. Estuary derivations support joins across multiple collections, long-lived transform progress, stateful lambdas, and even cyclic graphs ([Estuary derivations](https://docs.estuary.dev/concepts/derivations/)). Redpanda documents a cache/branch pattern for joining streams ([joining streams cookbook](https://docs.redpanda.com/connect/cookbooks/joining_streams/)). Limitation: Redpanda’s documented pattern is user-built cache choreography, not a general relational join; Estuary’s non-transactional materializations are only at-least-once.

6. **P0 — Stateful keyed aggregations/reductions.** Define reduce functions (sum, merge, last-write-wins, custom state) over keyed records and persist the accumulator with checkpoints. Estuary collection reduction annotations and derivation state cover this model; materializations continuously reduce collection documents into endpoint state ([derivations](https://docs.estuary.dev/concepts/derivations/), [materializations](https://docs.estuary.dev/concepts/materialization/)). Limitation: a non-idempotent reduction can be applied twice after a partial failure; Estuary explicitly calls out the at-least-once risk for non-transactional endpoints.

7. **P0 — Windowing and batch-aware operators.** Make count, byte-size, processing-time, event-time, and end-of-period windows first-class, with flush, late-arrival, ordering, and partial-window behavior documented. Redpanda treats messages as multi-part batches and supports batch boundaries by count, bytes, duration, or a predicate; NiFi’s `MergeContent` groups FlowFiles into a batch ([Redpanda batching](https://docs.redpanda.com/connect/configuration/batching/), [NiFi MergeContent](https://nifi.apache.org/components/org.apache.nifi.processors.standard.MergeContent/)). Limitation: Redpanda warns that pre-existing batches can bypass a downstream batch policy unless explicitly split; NiFi MergeContent is not intended for cron-driven scheduling.

8. **P1 — External lookup/cache with TTL and deduplication semantics.** Offer cache get/set/add/delete, TTL, negative/missing-key policy, and a clear distinction between enrichment cache, idempotency key store, and deduplication. Bento’s cache supports these operators and per-key TTL where the backend permits it; its cached processor memoizes expensive enrichment by key ([Bento cache](https://warpstreamlabs.github.io/bento/docs/components/processors/cache/), [Bento cached](https://warpstreamlabs.github.io/bento/docs/components/processors/cached/)). Limitation: Bento’s `cached` format is its own versioned format and cannot consume a pre-populated cache created by an unrelated producer.

### Stateful extraction, APIs, and scheduling

9. **P0 — Durable cursor/bookmark state as a source contract.** A source should declare cursor field/type, inclusive/exclusive boundary, initial value, commit timing, rewind/lag policy, and behavior when a cursor is absent or non-monotonic. Meltano stores incremental replication state by stable state ID; dlt’s incremental resource stores the latest cursor and describes missing/null cursor failures ([Meltano integration](https://docs.meltano.com/guide/integration), [Meltano state backends](https://docs.meltano.com/concepts/state_backends), [dlt cursor](https://dlthub.com/docs/general-usage/incremental/cursor)). Limitation: dlt warns unordered source data can cause missed or duplicate rows; its incremental mechanism is not itself a deduplicating merge.

10. **P0 — Declarative REST ingestion with pagination variants.** Model page-number, offset/limit, body/JSON link, header link, and response-cursor pagination, with configurable data selection and stop conditions. dlt’s REST source ships these paginator classes and automatic detection ([dlt REST API source](https://dlthub.com/docs/dlt-ecosystem/verified-sources/rest_api/basic), [REST helpers](https://dlthub.com/docs/dlt-ecosystem/verified-sources/rest_api/advanced)). Limitation: dlt documents pagination as GET-only for most paginator types; POST pagination requires a custom paginator, and production configurations should make the paginator explicit when autodetection is uncertain.

11. **P0 — Cursor-plus-pagination API extraction with atomic progress.** Persist progress only after the corresponding page/record is durably accepted, and support APIs whose returned cursor must be converted before the next request. dlt supports incremental request parameters, cursor paths, conversion functions, and pagination in one declarative REST configuration ([dlt REST API source](https://dlthub.com/docs/dlt-ecosystem/verified-sources/rest_api/basic)). Limitation: dlt’s older `incremental` endpoint field is documented as deprecated in favor of the placeholder method; custom API behavior still requires Python paginator code.

12. **P1 — API authentication, rate limiting, retry, and backoff as reusable resources.** Separate credentials from flow definitions; support token/basic/OAuth2 auth, per-service rate limits, retryable status classes, and `Retry-After` handling. dlt supports token/basic/custom auth and request retries/timeouts; Redpanda’s HTTP client supports OAuth2, rate limits, retries, and streaming reconnect; its rate-limit resources can be shared across components ([dlt REST authentication](https://dlthub.com/docs/dlt-ecosystem/verified-sources/rest_api/basic), [Redpanda HTTP client](https://docs.redpanda.com/connect/components/inputs/http_client/), [Redpanda rate limits](https://docs.redpanda.com/connect/components/rate_limits/about/)). Limitation: a rate limit is not a correctness checkpoint; after a crash the source still needs durable cursor state.

13. **P1 — Scheduled polling and time-zone-aware triggers.** Make periodic API/table polling, cron expressions, time zones, overlap policy, and missed-run behavior explicit. Redpanda’s `generate` input accepts durations and cron expressions with IANA time-zone prefixes; Meltano schedules named jobs or EL tasks and maps schedule names to state IDs ([Redpanda generate](https://docs.redpanda.com/connect/components/inputs/generate/), [Meltano orchestration](https://docs.meltano.com/guide/orchestration/), [Meltano CLI schedule](https://docs.meltano.com/reference/command-line-interface)). Limitation: Redpanda’s generate input is a trigger inside one runtime, not a durable multi-node scheduler; Meltano delegates actual schedule execution to Airflow or another orchestrator.

14. **P1 — Run parameters, environments, and metadata-driven reuse.** Parameterize endpoints, datasets, credentials references, and limits by environment/run; validate required parameters before execution and preserve scope. Hop provides declared pipeline/workflow parameters, variable scopes, environment/run configurations, and runtime metadata injection ([Hop variables](https://hop.apache.org/manual/latest/variables.html), [metadata injection](https://hop.apache.org/manual/latest/pipeline/transforms/metainject.html), [projects/environments](https://hop.apache.org/manual/latest/projects/index.html)). Limitation: Hop warns local variables are not thread-safe in a pipeline and cannot be set and consumed reliably by sibling transforms running in parallel.

15. **P2 — OpenAPI-to-source/pipeline generation.** Generate a typed API source from OpenAPI, including endpoint relationships, pagination, auth placeholders, and schema hints, while retaining a reviewable generated specification. dlt documents an OpenAPI source generator that creates declarative REST configurations and discovers pagination per endpoint ([dlt OpenAPI generator](https://dlthub.com/docs/dlt-ecosystem/verified-sources/openapi-generator)). Limitation: generated configuration still needs API-specific review for non-standard pagination, semantics, rate limits, and incomplete OpenAPI descriptions.

### Transformations, data quality, and contracts

16. **P0 — Embedded transformation DSL with safe typed failure.** Provide a reusable expression/mapping language for projection, filtering, nesting, metadata, arithmetic, and explicit deletion/error values; compile/lint it before deployment. Redpanda uses Bloblang for mapping and interpolation; Bento uses Bloblang for payload/metadata mappings; Estuary supports SQL and lambda derivations ([Bento Bloblang](https://warpstreamlabs.github.io/bento/docs/guides/bloblang/about/), [Redpanda processors](https://docs.redpanda.com/connect/components/processors/about/), [Estuary SQL derivation](https://docs.estuary.dev/guides/derivation_tutorial_sql/)). Limitation: Redpanda’s arbitrary SQL processor is deprecated in favor of narrower SQL processors, illustrating the need to keep the supported transformation surface coherent.

17. **P0 — Schema contracts at every collection/edge.** Validate each document/record against an explicit schema before buffering or publishing; define required fields, key paths, types, nullability, precision, and unknown-field behavior. Estuary validates collection documents on write/read and requires a key plus schema; dlt supports table/column/data-type schema-contract modes ([Estuary collections](https://docs.estuary.dev/concepts/collections/), [dlt schema contracts](https://dlthub.com/docs/general-usage/schema-contracts)). Limitation: dlt’s default `evolve` mode adds columns and can create variant columns; it also offers destructive `discard_row`/`discard_value`, which must never be silently selected by a data-preserving system.

18. **P0 — Explicit schema-evolution workflow and compatibility policy.** Detect additions, removals, key changes, type/precision changes, and incompatible destination changes before side effects; require approval/backfill/recreate/abort policy per binding. Estuary treats the collection spec as a contract and can coordinate schema evolutions across captures, derivations, and materializations ([schema evolution guide](https://docs.estuary.dev/guides/schema-evolution/), [schema evolution concept](https://docs.estuary.dev/concepts/advanced/evolutions/)). Limitation: incompatible backfills may drop/recreate destination tables and lose custom DDL; Estuary documents `abort`, `disableBinding`, and `disableTask` alternatives ([backfilling](https://docs.estuary.dev/reference/backfilling-data/)).

19. **P1 — Data-quality assertions and executable pipeline tests.** Permit fixtures, expected derived documents, row/column checks, and contract tests to run before publish and in CI, with failures blocking deployment or quarantining data. Estuary catalog tests ingest fixtures and verify derived collection contents; Hop has pipeline unit-test metadata with alternative data sets and golden outputs ([Estuary core concepts](https://docs.estuary.dev/concepts/), [Hop metadata types](https://hop.apache.org/manual/latest/metadata-types/index.html)). Limitation: fixture tests do not prove external connector behavior, rate-limit behavior, or destination transaction guarantees.

20. **P1 — Validation/quarantine policy for malformed records.** Define whether a bad record fails the batch, routes to a durable quarantine/DLQ with error context, or is repaired by an explicitly configured transformation; never silently drop it. Bento documents `try`, `catch`, `retry`, `reject_errored`, fallback, and switch-based dead-letter routing; Redpanda supports strict error handling or explicit error-flag routing ([Bento error handling](https://warpstreamlabs.github.io/bento/docs/configuration/error_handling/), [Redpanda error handling](https://docs.redpanda.com/connect/configuration/error_handling/)). Limitation: dropping an errored message propagates an acknowledgement upstream in these runtimes, so the policy must make data loss a deliberate choice.

21. **P0 — Primary-key deduplication and deterministic merge policy.** Make identity, dedup key, tie-breaker, delete semantics, and replay idempotency explicit. dlt supports append/full/merge dispositions, primary-key deduplication, and deterministic `dedup_sort`; Estuary keys collections and reduces documents by key ([dlt merge loading](https://dlthub.com/docs/general-usage/merge-loading), [Estuary collections](https://docs.estuary.dev/concepts/collections/)). Limitation: dlt documents arbitrary dedup choice when no sort is configured; Estuary reduction semantics must match the destination’s transaction guarantees.

22. **P1 — Reusable SQL/database lookups and query transforms.** Allow a record to parameterize a safe SQL select/insert/raw statement, return rows into the record, and distinguish static prepared parameters from unsafe dynamic SQL. Redpanda and Bento provide `sql_select` and related SQL processors, with argument mappings and supported-driver lists ([Redpanda SQL](https://docs.redpanda.com/connect/components/processors/sql/), [Bento SQL select](https://warpstreamlabs.github.io/bento/docs/components/processors/sql_select/)). Limitation: both document narrower replacement processors because arbitrary SQL is deprecated or less safe; connector-specific driver availability and query cost still need admission control.

### Replay, durability, lineage, and operations

23. **P0 — Durable replayable history separate from destination state.** Retain an append-only journal/history that can be read from arbitrary offsets to rebuild derivations/materializations without re-reading a source. Estuary collections/journals retain historical documents in object storage and allow readers to start at any offset ([Estuary journals](https://docs.estuary.dev/concepts/advanced/journals/), [collections](https://docs.estuary.dev/concepts/collections/)). Limitation: storage retention and bucket lifecycle policies determine how far back replay remains possible.

24. **P0 — Checkpointed, transactional source/sink progress.** Commit source offsets/cursors together with destination effects or an idempotent recovery record; expose the exact last committed point and retry behavior. Estuary’s materialization protocol has acknowledge/load/store phases, checkpoints, and a transactional recovery log; dlt retains load packages and pipeline state and supports retrying failed jobs ([Estuary materialization protocol](https://docs.estuary.dev/reference/Connectors/materialization-protocol/), [dlt pipeline](https://dlthub.com/docs/general-usage/pipeline), [dlt run a pipeline](https://dlthub.com/docs/walkthroughs/run-a-pipeline)). Limitation: exactly-once requires a transactional or idempotent destination apply; neither a cursor nor a local load package alone provides it.

25. **P0 — User-directed provenance and event replay.** Record source/destination path, processor/task versions, timestamps, attempts, and content identity; allow replay of a selected event or range from a stable provenance view. NiFi’s Data Provenance supports search, event details, graphical lineage, and replay; its UI also exposes “Replay last event” ([NiFi user guide](https://nifi.apache.org/nifi-docs/user-guide.html)). Limitation: replay can re-run side effects, so a safe implementation needs idempotency or an explicit destination/replay mode.

26. **P1 — Backfill, incremental backfill, and full reset as named operations.** Distinguish “rebuild destination from retained history,” “re-read selected source ranges,” and “reset the entire flow,” showing affected bindings, downtime, retention, and destructive consequences. Estuary documents materialization backfill, incremental backfill, and dataflow reset with separate semantics ([backfilling data](https://docs.estuary.dev/reference/backfilling-data/)). Limitation: Estuary warns that some incompatible schema changes cause drop/recreate and that routine backfills can create downtime or duplicate delta updates.

27. **P1 — Queue back pressure, bounded buffering, and expiry.** Configure object/byte thresholds, durable or memory buffer choice, queue expiry, and upstream pause behavior; expose queue depth and oldest age. NiFi applies object-count and data-size back-pressure thresholds; Redpanda’s no-buffer mode propagates output back pressure to the input and recommends a durable broker for relief ([NiFi user guide](https://nifi.apache.org/nifi-docs/user-guide.html), [Redpanda no buffer](https://docs.redpanda.com/connect/components/buffers/none/)). Limitation: buffering can improve availability while increasing replay/storage complexity; a memory-only buffer is not a durable recovery point.

28. **P1 — Per-task/shard throughput and lag statistics.** Report input/output counts and bytes, latency, checkpoints, errors, queue age, shard balance, and transform-level counters with stable labels. Estuary exposes stats per shard, task type, collection, transform, registers, documents, and bytes; Bento exposes metrics, health/readiness, and tracing ([Estuary logs/statistics](https://docs.estuary.dev/reference/working-logs-stats/), [Bento monitoring](https://warpstreamlabs.github.io/bento/docs/guides/monitoring/)). Limitation: metrics are not a lineage substitute; counts and timings must be correlated with run/checkpoint IDs to diagnose data correctness.

29. **P1 — Elastic, fault-tolerant task shards and no-downtime split.** Partition stateful work by key, recover shards independently, and split/redistribute hot or large work without stopping the task. Estuary describes fault-tolerant stateful shards assigned to a scalable compute pool and split without downtime ([task shards](https://docs.estuary.dev/concepts/advanced/shards/)). Limitation: sharding stateful joins/reductions requires a stable shuffle/key contract and careful repartitioning; a generic worker restart is not equivalent.

30. **P1 — Cluster HA with leader/primary-node or equivalent ownership semantics.** Define how workers coordinate, how singleton source pollers are elected, how state is shared, and how a failed node’s work is reassigned. NiFi documents zero-leader clustering, a cluster coordinator, a ZooKeeper-elected primary node, and isolated processors for singleton external pollers ([NiFi administration guide](https://nifi.apache.org/nifi-docs/administration-guide.html), [NiFi overview](https://nifi.apache.org/nifi-docs/overview.html)). Limitation: “run every node” is unsafe for non-idempotent polling; singleton ownership must be part of the source contract, not merely deployment advice.

31. **P1 — Runtime stream/task lifecycle API with validation and readiness.** Create, inspect, update, pause, resume, and delete independently isolated streams/tasks through a control API; validate before activation and provide readiness/status endpoints. Redpanda Connect and Bento both document a `streams` mode with isolated input/buffer/pipeline/output and HTTP create/read/update/delete APIs ([Redpanda streams API](https://docs.redpanda.com/connect/guides/streams_mode/streams_api/), [Bento streams API](https://warpstreamlabs.github.io/bento/docs/guides/streams_mode/streams_api/)). Limitation: Bento’s update shuts down the old stream before replacing it; a production implementation should define drain, checkpoint, and rollback behavior.

32. **P0 — Secrets, RBAC, and parameter scopes as part of the flow contract.** Keep secrets out of published flow specs/logs, authorize who can read/change a credential or parameter, and revalidate affected components after a secret/parameter update. NiFi encrypts sensitive flow values, supports sensitive Parameter Context values and fine-grained access policies; dlt’s REST source documents external secret configuration; Hop supports variable/secret-manager resolution ([NiFi admin guide](https://nifi.apache.org/nifi-docs/administration-guide.html), [NiFi user guide](https://nifi.apache.org/nifi-docs/user-guide.html), [dlt REST auth](https://dlthub.com/docs/dlt-ecosystem/verified-sources/rest_api/basic), [Hop variables](https://hop.apache.org/dev-manual/next/architecture/variables-and-metadata.html)). Limitation: a secret provider does not by itself prevent unsafe dynamic SQL, URL SSRF, or accidental payload logging; those remain separate validation boundaries.

## Connector examples (deliberately not counted as feature gaps)

The products demonstrate useful connector breadth, but connector count is a separate workstream from ETL-flow semantics. These examples are evidence for potential acceptance tests or connector priorities, not claims about Transferia’s current catalog:

- **NiFi:** its official component catalog/getting-started documentation lists routing/record processors and source/destination families such as FTP/SFTP/S3/GCS, databases, Kafka, HTTP, and cloud services ([component index](https://nifi.apache.org/docs/nifi-docs/), [getting started](https://nifi.apache.org/nifi-docs/getting-started.html)).
- **Estuary Flow:** captures/materializations are connector tasks around collections, with the catalog separating source capture from destination materialization ([core concepts](https://docs.estuary.dev/concepts/), [materializations](https://docs.estuary.dev/concepts/materialization/)).
- **Redpanda Connect:** the component catalog covers Kafka and many brokers, HTTP, SQL databases, object stores, caches, cloud services, and schema-registry components ([component catalog](https://docs.redpanda.com/connect/components/about/)).
- **Bento:** the component docs expose inputs, processors, outputs, caches, buffers, and service endpoints; the product is intentionally a composable stream runtime rather than a warehouse-specific connector catalog ([streams mode](https://warpstreamlabs.github.io/bento/docs/guides/streams_mode/about/)).
- **Apache Hop:** the manual describes hundreds of transforms and pluggable database/cloud/file integrations, with metadata-driven connection and execution objects ([Hop manual](https://hop.apache.org/manual/latest/), [metadata-driven architecture](https://hop.apache.org/manual/latest/metadata-driven-architecture.html)).
- **Meltano:** extractor/loader plugins are commonly Singer taps/targets, with optional mappers and dbt/utility tasks; the project can install and lock plugin definitions ([integration guide](https://docs.meltano.com/guide/integration), [plugins](https://docs.meltano.com/concepts/plugins)).
- **dlt:** the verified-source catalog includes REST APIs and sources for services/databases such as GitHub, Google Ads, HubSpot, Kafka, MongoDB, Postgres Replication, Salesforce, Shopify, Slack, and Stripe ([verified sources](https://dlthub.com/docs/dlt-ecosystem/verified-sources)).

## Cross-product limitations worth preserving in the eventual design

1. **A cursor is not a checkpoint.** dlt, Meltano, and API clients expose cursor state, but correctness still depends on when that state commits relative to destination effects.
2. **A batch/window is not a transaction.** Redpanda/Bento batch operators make grouping convenient; they do not automatically make side effects atomic.
3. **A schema contract must not silently discard data.** dlt documents discard modes as options; a data-preserving default should reject or quarantine with explicit user intent.
4. **A replay button is an operationally dangerous capability.** NiFi’s replay and Estuary/dlt backfills are valuable, but each needs idempotency, scope preview, and an explicit destructive-impact warning.
5. **External schedulers and worker HA are separate concerns.** Meltano delegates schedule execution to Airflow/another orchestrator, while NiFi/Estuary provide runtime coordination; a Transferia design should name which layer owns each guarantee.

## Local audit: control-plane/runtime/registry/frontend (bounded read-only pass)

This section records evidence from the repository, not competitor research. It is intentionally limited to the control plane, runtime, registry, server contracts, and the frontend application boundary. “Not represented” means not present in the inspected contracts/files; it is not a claim that a wider repository or deployment layer cannot provide it.

### 1. Auth, RBAC, multitenancy, and audit — partial; user-facing authorization is unrepresented in inspected paths

- The HTTP surface is a local control plane with a loopback-origin guard. `router` mounts lifecycle/configuration/log routes without an auth extractor ([`crates/transferia-control-plane/src/server/http.rs:141-198`](../../../crates/transferia-control-plane/src/server/http.rs#L141-L198)); `enforce_loopback_origin` checks only `Host`/`Origin` authorities ([`http.rs:226-271`](../../../crates/transferia-control-plane/src/server/http.rs#L226-L271)).
- Non-loopback exposure requires an explicit opt-in and emits a warning, but the server bootstrap does not install user authentication or authorization ([`crates/transferia-control-plane/src/server/mod.rs:18-41`](../../../crates/transferia-control-plane/src/server/mod.rs#L18-L41)). This is a meaningful local-boundary safeguard, not RBAC.
- Persisted `DeliveryRecord` has identity, config, revision, runtime, and timestamps, but no owner, tenant, actor, ACL, or audit-event fields ([`crates/transferia-server-contracts/src/lib.rs:58-84`](../../../crates/transferia-server-contracts/src/lib.rs#L58-L84)). The JSON store is one process/state directory protected by a file lock ([`crates/transferia-control-plane/src/server/store.rs:44-93`](../../../crates/transferia-control-plane/src/server/store.rs#L44-L93)).

**Assessment:** partial for local exposure hardening; candidate P0/P1 gap for authenticated multi-user access, tenant isolation, per-resource RBAC, and append-only actor/audit events. Repository-wide auth integration is unknown because this pass did not inspect deployment or external identity layers.

### 2. Schedules, dependencies, run history — lifecycle/revisions/logs present; scheduling and DAG history unrepresented in inspected contracts

- The API exposes list/get/create/update/delete, validate, activate, stop, and worker-log endpoints, but no schedule, dependency, run-list, or history route in the mounted route set ([`crates/transferia-control-plane/src/server/http.rs:152-181`](../../../crates/transferia-control-plane/src/server/http.rs#L152-L181)).
- A delivery has optimistic `revision` and `record_version`, current `ValidationState`, current `RuntimeState`, and created/updated timestamps ([`crates/transferia-server-contracts/src/lib.rs:18-84`](../../../crates/transferia-server-contracts/src/lib.rs#L18-L84)). On server restart, an in-progress current state is normalized to `Stopped`; this preserves a safe current-state invariant but does not retain a run-history record ([`lib.rs:109-121`](../../../crates/transferia-server-contracts/src/lib.rs#L109-L121)).
- Per-run worker logs are retained under `runs/<delivery>/<run>.log` and listed/read with byte cursors ([`crates/transferia-control-plane/src/server/logs.rs:10-126`](../../../crates/transferia-control-plane/src/server/logs.rs#L10-L126)); this is useful diagnostics, but it is not a structured run ledger containing start/end/status/checkpoint/actor/trigger/dependency information.

**Assessment:** partial for manual start/stop, current status, optimistic revisions, and log retrieval; candidate gap for durable cron/event schedules, dependency-aware execution, run history, backfill/run selection, and schedule ownership. Broader CLI/deployment scheduling is unknown rather than asserted absent.

### 3. Metrics exporters and SLA alerts — rich local console statistics; external export/alerting unknown
