# ETL/data-integration platform feature benchmark (2026-09-19)

## Scope and interpretation

This is a research input for a Transferia Rust gap review, not an assertion that Transferia lacks any item below. Each row is a **candidate feature to verify against the codebase**. Connector catalog breadth is intentionally out of scope; this compares operational and platform capabilities around pipelines, replication, recovery, governance, and ELT.

The comparison covers Airbyte (Cloud and self-managed/OSS where the documentation distinguishes them), the Fivetran/HVR family (Fivetran managed service plus HVR distributed replication), Striim (Platform/Cloud), IBM StreamSets (Control Hub/Data Collector), Informatica Cloud Data Ingestion and Replication, Azure Data Factory, Qlik Talend Cloud/Data Integration, and CData Sync. Availability, source/target support, and plan/edition limitations are called out rather than generalized.

Priorities are product-risk priorities for a durable data-movement platform, not a statement of current Transferia maturity:

- **P0** — correctness, recoverability, or operational safety; failure can lose, duplicate, or silently misapply data.
- **P1** — materially improves production operations, governance, or scale.
- **P2** — workflow/productivity capability that becomes important as the platform grows.

## Cross-cutting conclusions for prioritization

1. **Recovery is a product contract, not just a retry loop.** The strongest common pattern is a durable source position plus destination-aware restart policy (Airbyte state, Striim checkpoints, StreamSets offsets, HVR capture state). The report should distinguish replay, duplicate tolerance, commit barriers, and true losslessness.
2. **Schema drift needs an explicit policy and a second runtime boundary.** Competitors expose “apply/ignore/pause/stop” choices and document unsupported changes. A generic “auto-evolve” switch without source/target capability checks would be unsafe.
3. **Initial load and CDC are separate phases with a handoff.** Striim and HVR make snapshot parallelism/restartability and CDC cutover visible as first-class operations; a single undifferentiated “sync” abstraction can hide the hardest correctness cases.
4. **Reconciliation is distinct from observability.** Lag, status, and logs do not prove source-target equality. HVR Compare and Striim validation dashboards are explicit integrity checks; row/checksum diff, repair policy, and evidence retention deserve separate requirements.
5. **Enterprise readiness clusters around governance and deployment.** RBAC, tenant/project isolation, audit export, secret lifecycle, private workers, and failover appear across multiple products, but plan and edition boundaries are substantial. Requirements should identify the minimum Transferia edition and avoid silently promising enterprise features in the base runtime.

## Focused primary-source verification: HVR 6 and Striim

The following replaces broad product-overview evidence with exact operational sections for the five requested deep-dive topics. These are particularly useful acceptance-criteria candidates when a platform already has basic CDC, preflight, retries, checkpoints, and preview.

### 1. Parallel CDC apply/integrate: ordering and transaction caveats

- **HVR 6 parallel integrate is table-group partitioning, not unrestricted row parallelism.** HVR documents that one integrate job processes changes for multiple tables sequentially; the supported procedure is to suspend capture, drain and suspend integrate, assign tables exclusively to new groups, duplicate the target location, and create separate Integrate actions. It then says replication continues from where it stopped. ([How Can I Create Multiple Integrate Jobs to Run Simultaneously?](https://fivetran.com/docs/hvr6/faq/how-to/multiple-integrate-jobs-running-simultaneously))
- **HVR 6 exposes the ordering trade-off in the Integrate method.** `CONTINUOUS` applies each `INSERT`/`UPDATE`/`DELETE` in original captured order. `BURST` sorts/coalesces and applies set-wise, so order differs from capture order; target triggers can fire in the wrong order, and Burst is incompatible with foreign-key constraints and collision detection. `TxSplitLimit` can split very large transactions to bound resource use, but cannot be combined with Burst. ([Integrate action reference](https://fivetran.com/docs/hvr6/action-reference/integrate))
- **Striim parallel writers require a deterministic distribution policy.** Generic database writers can distribute events round-robin and are documented for initial load only; recovery disables parallel threads for those writers. Kafka writers hash by topic so a topic remains on one instance. For ClickHouse, Striim explicitly warns that scattering one key across writers can interleave/clobber updates; partitioning must use the target sorting key. ([Creating multiple writer instances](https://www.striim.com/docs/en/creating-multiple-writer-instances--parallel-threads-.html), [ClickHouse writer operational considerations](https://striim.com/docs/en/clickhouse-writer-operational-considerations.html))
- **Striim’s delivery-semantics page makes transaction batching observable.** A source transaction can span multiple Kafka transactions under an EventCount commit policy; DDL rolls the current buffer and is emitted as its own transaction; batches across topic partitions run in parallel, while batches for one topic-partition are sequential. ([Select Delivery Semantics](https://www.striim.com/docs/en/select-delivery-semantics.html))

**Candidate gap wording:** a destination-aware “parallel apply” contract must define partition key, per-key order, cross-table/transaction ordering, DDL barriers, recovery compatibility, and whether splitting a source transaction is allowed.

### 2. Intra-table snapshot slicing and restart/resume

- **HVR 6 Refresh supports intra-table slicing.** The UI supports modulo, boundary, count, and series slicing; the operator can choose the slice column, number/boundaries, and a subset of slices. The docs warn that slicing on a non-key/unstable column can move a row between slices and cause duplicate processing or data loss. ([Refreshing Data](https://fivetran.com/docs/hvr6/user-interface/channels/refreshing-data))
- **HVR’s CLI makes the stability requirement explicit.** `hvrrefresh -S` requires a stable slicing column; if rows move between slices, a row can be processed twice or not at all. `-a`/`-A` controls suggested slice count/rows per slice, and `-s` leaves a refresh job suspended for later invocation. ([hvrrefresh command reference](https://fivetran.com/docs/hvr6/command-line-interface/command-reference/hvrrefresh?selectedPageVersions=16&selectedPageVersions=17))
- **HVR 6 controls slice fan-out and safe suspension.** `quota_run` limits how many jobs are RUNNING/HANGING (useful when a sliced refresh creates one job per table), while `quota_speed` limits scheduler start rate. A graceful suspension waits for the current replication cycle to complete so pending transactions are not left behind; force suspension may leave a job pending. ([Job Attributes](https://fivetran.com/docs/hvr6/internal-objects/job-attributes), [HVR Jobs](https://fivetran.com/docs/hvr6/user-interface/jobs))
- **Striim Fast Snapshot Recovery is table-granular, not row/slice-granular.** After an interrupted initial load, completed tables are not reread; incomplete tables restart from the beginning. With partition-aware read, already-read partitions are still reread from the beginning. The operator chooses keep/replace/truncate behavior for partial target tables, with “keep” explicitly risking duplicates. ([Fast Snapshot Recovery during initial load](https://striim.com/docs/en/fast-snapshot-recovery-during-initial-load.html), [Fast Snapshot Loading](https://striim.com/docs/platform/en/fast-snapshot-loading.html))

**Candidate gap wording:** resumable snapshots should persist completed slice/table manifests, use a stable snapshot boundary, and define duplicate-safe restart behavior rather than merely rerunning incomplete work.

### 3. CDC buffer-to-disk and large-transaction spill

- **HVR 6 spills in-flight transaction state after a memory threshold.** The Agent Disk Requirements page says CDC stores in-flight transactions in memory until a threshold, then writes additional change data to disk; it also describes transaction-file accumulation on the hub when capture outruns integrate. ([HVR Agent Disk Requirements](https://fivetran.com/docs/hvr6/install-and-upgrade/system-requirements/agent-disk-requirements), [HVR Hub Disk Requirements](https://fivetran.com/docs/hvr6/install-and-upgrade/system-requirements/hub-disk-requirements))
- **HVR checkpoint tuning makes long-transaction recovery configurable.** Capture checkpoint files store uncommitted long-running transaction changes; frequency, storage location, and retention are configurable. Without checkpoints, restart rewinds to the oldest open transaction and may require old DBMS logs. ([Tuning Capture Checkpoints](https://fivetran.com/docs/hvr6/advanced-operations/tuning-capture-checkpoints))
- **HVR documents large-transaction temporary-file failure modes and controls.** `HVR_TEMP_SPILL` controls capture-side RAM before temporary files; `HVR_SORT_BYTE_LIMIT` controls integrate-side sort spill; insufficient disk can fail with “No space left on device.” ([High Latency While Processing Large Transactions Using Temporary Files](https://fivetran.com/docs/hvr6/faq/expert-notes-best-practices/latency-large-transactions))
- **Striim has reader-specific transaction spill.** Oracle Reader spills transactions to Striim server disk after the default 100 MB memory threshold; OJet spills after a transaction-age or operation-count threshold. SQL Server Reader’s default Disk buffer spills when a transaction exceeds the configured spillover size, and recovery restarts previously buffered transactions from the beginning. ([Oracle database troubleshooting](https://striim.com/docs/platform/en/oracle-database-troubleshooting.html), [SQL Server programmer’s reference](https://developer.striim.com/onlinedocs/en/sql-server-programmer-s-reference.html))
- **Striim’s Kafka delivery docs warn that large commit buffers can OOM or exceed transaction timeouts.** The documented controls are smaller Commit Policy, more memory, and broker/client transaction timeout alignment. ([Select Delivery Semantics](https://www.striim.com/docs/en/select-delivery-semantics.html))

**Candidate gap wording:** configurable spill thresholds, disk placement/retention, spill metrics, and explicit replay semantics for spilled transactions should be part of the CDC runtime contract.

### 4. Source-load throttling and resource limits

- **HVR 6 throttles scheduler concurrency/start rate.** `quota_run` caps concurrently running/hanging jobs (including sliced refresh jobs); `quota_speed` limits job starts per time window. ([Job Attributes](https://fivetran.com/docs/hvr6/internal-objects/job-attributes))
- **HVR documents capacity sizing and resource locality.** Resource-heavy capture/integrate processing is intended to run on Agents; the Hub primarily orchestrates and stores state. HVR gives sizing bands by channels and change rate, plus storage/IO guidance. ([HVR Hub Disk Requirements](https://fivetran.com/docs/hvr6/install-and-upgrade/system-requirements/hub-disk-requirements), [HVR Agent Disk Requirements](https://fivetran.com/docs/hvr6/install-and-upgrade/system-requirements/agent-disk-requirements))
- **Striim applies explicit cluster resource policies.** Limits include applications per CPU, applications per GB of JVM memory, cluster size, API call rate, active users, UI sessions, and ad-hoc queries. Reaching a limit fails the action with `ResourceLimitException`, rather than silently overcommitting the cluster. ([Resource usage policies](https://www.striim.com/docs/en/resource-usage-policies.html))
- **Striim uses backpressure as source-load protection and observability.** Streams have finite capacity; when full, upstream processing is backpressured and an alert is emitted. ([Understanding and managing backpressure](https://new.striim.com/docs/en/understanding-and-managing-backpressure.html))

**Candidate gap wording:** expose per-job/per-source concurrency, throughput or rate limits, memory/disk budgets, backpressure state, and fail-closed behavior when limits are reached.

### 5. Pinned runtime versions, compatibility, and rollback expectations

- **HVR 6 has an explicit release lifecycle and compatibility model.** HVR 6.1/6.2/6.3 support windows are listed; HVR 6 is incompatible with HVR 5, while 6.x major versions are network-compatible only within documented boundaries. Feature/bug fixes require upgrading the machine that performs the relevant operation (for example, Integrate), not merely the Hub. ([HVR 6 Release Life Cycle](https://fivetran.com/docs/hvr6/getting-started/release-life-cycle), [Upgrading HVR 6](https://fivetran.com/docs/hvr6/install-and-upgrade/upgrade))
- **HVR’s HVR 5→6 upgrade path preserves replication state only through the prescribed procedure.** The documentation says HVR 6 is not compatible with 5.x/4.x and describes a three-phase upgrade without Refresh, while a channel-definition-only migration does not preserve replication state. ([Upgrading from HVR 5](https://fivetran.com/docs/hvr6/install-and-upgrade/upgrade/upgrading-from-hvr-5), [Important Notes When Upgrading](https://fivetran.com/docs/hvr6/install-and-upgrade/upgrade/upgrading-from-hvr-5/important-notes-when-upgrading-from-hvr-5))
- **Striim pins server and Forwarding Agent compatibility.** Current 5.4.2 guidance requires the first three version components to match between Agent and server; some releases require a specific Agent version. ([What’s new in Striim Platform 5.4.2](https://www.striim.com/docs/platform/en/what-s-new-in-striim-platform-5-4-2.html))
- **Striim explicitly documents non-rollback upgrade boundaries.** Platform 5.4.0.2 requires JDK 17 and cannot downgrade afterward; Striim Cloud upgrades similarly state that downgrade is not possible after the JDK change. ([Striim 5.4.2 release notes](https://www.striim.com/docs/platform/en/release-notes.html), [Upgrading Striim Cloud](https://striim.com/docs/en/upgrading-striim-cloud.html))
- **Striim deployment groups pin placement, not adapter binaries.** Deployment groups constrain which servers/Forwarding Agents run an application and can set minimum servers/application limits; redeployment is required for membership changes to take effect. ([Managing deployment groups](https://www.striim.com/docs/en/managing-deployment-groups.html))

**Candidate gap wording:** a production platform should pin runtime/connector versions, validate cross-component compatibility before rollout, support staged promotion, and state whether rollback is supported or intentionally impossible.

### CData Sync schema-evolution citation verification

The cited [CData Sync Features page](https://cdn.cdata.com/help/ASN/sync/Features.html) directly supports the prior report’s wording. In its **Schema Changes** section, it says each run compares source and destination schemas; missing source columns are added to the destination; an increased source type size widens the destination column (for example, `varchar(255)` → `varchar(2000)` or `smallint` → `integer`); and it explicitly says Sync never deletes destination columns or reduces destination type size when the source narrows. This is an add/widen-only, loss-averse evolution policy, not a general claim that CData applies arbitrary DDL.
