# Чего не хватает Transferia Rust относительно ETL/data-integration инструментов

Дата исследования: **19 сентября 2026**. Проверенная ревизия Transferia: `5282923723023b6cf7b6193393a0ef4a6baff73c`.

## Короткий вывод

Главное отставание — не количество коннекторов, а **масштабирование больших загрузок, возобновление работы и эксплуатация длительно живущих pipelines**.

Первые инвестиции я бы направил в:

1. Распил одной PostgreSQL/MySQL-таблицы на параллельные snapshot chunks.
2. Возобновляемый initial load и дозагрузку диапазонов без полного рестарта.
3. Контролируемую эволюцию схем с сохранением правильной схемы для replay.
4. Сверку данных источника и назначения, поиск расхождений и управляемый repair.
5. Безопасный replay SQL-записи при ambiguous commit: связать destination effects и progress.
6. Параллельное применение CDC с явно заданными гарантиями порядка.
7. HA/recovery, наблюдаемость отставания и безопасное управление checkpoint/state.

**Важно:** один последовательный WAL reader не означает однопоточный CDC pipeline. Чтение журнала, декодирование, преобразования и применение независимых изменений — разные стадии. У Transferia уже есть конкурентные partition tasks и отдельные reader/parser/sink задачи; пробел № 6 касается безопасного параллельного apply, а не «разделить WAL на четыре части».

Ниже — **53 ранжированных функциональных пробела или неполных возможности**. Коннекторы перечислены отдельно. Это продуктовый backlog по результатам анализа, **не список 53 багов и не обещание реализовать всё**.

## Как проводилось сравнение

Три лёгких субагента параллельно исследовали 22 продукта/семейства по официальным документам и открытым исходникам. Основной агент проверил текущую Transferia, объединил повторы и исключил ложные пробелы. Дополнительные проходы проверили runtime/control-plane и точные ограничения конкурентных snapshot/apply механизмов.

Сравнение относится к встроенным возможностям этого checkout. Внешний cron, reverse proxy, отдельный Kafka или внутреннее расширение могут закрывать часть потребностей, но не считаются встроенной функцией продукта. Не проверялись все закрытые версии, каждый connector combination и поведение конкурентов экспериментом. Наличие функции в документации не доказывает её качество, скорость или пригодность для нашего lossless-контракта.

Обозначения:

- **Нет** — проверенные конфигурация/контракты/реализация не предоставляют описанную возможность.
- **Частично** — есть близкая функция, но указанного поведения не хватает. Колонка «Сейчас» объясняет разницу.
- **T1–T10** — проверяемые доказательства по локальным исходникам в [BASELINE.md](../docs/research/competitor-gaps-2026-09-19/BASELINE.md). Это не результат одного поиска по ключевому слову.
- Приоритет — моя оценка для высокопроизводительной, надёжной **one-way data integration**. Учитываются ущерб от сбоя, частота сценария, throughput/операционная польза и близость к текущему продукту. Номер задаёт убывающую важность; соседние пункты не имеют математически точного превосходства. Для публичного multi-user сервиса № 14 и № 29–30 становятся обязательными до запуска.

AWS DMS, Huawei DRS, Tencent DTS также исключены из выбранного корпуса: хотя у них есть continuous replication, для этой задачи достаточно более однозначных ETL/data-integration аналогов. Sling оставлен за регулярные ELT/incremental/backfill сценарии, а не за возможность разово скопировать БД.

## Уже есть — не считать пробелами

| Возможность | Что действительно есть в Transferia |
|---|---|
| CDC и переход snapshot→CDC | PostgreSQL/MySQL имеют native replication и exact handoff. Неуспешный старый benchmark не доказывает отсутствия CDC. T3 |
| Параллелизм | Между таблицами/partition tasks; OpenSearch PIT slices; YTsaurus PartitionTables; server/decode threads ClickHouse. T1–T2, T6 |
| Recovery и guarantees | Durable local state, CAS/leases, ordered source-commit barrier и connector-specific replay/idempotency уже есть. Итоговая гарантия зависит от source/sink pair: многие SQL/queue пути явно at-least-once при ambiguous write; нельзя писать ни «нет checkpoints вообще», ни «везде exactly-once». T6, T8 |
| Schema validation | Общий preflight, native/Arrow/destination type contracts и runtime checks. Нет именно общей online evolution. T4, T8 |
| SQL/простые transforms | DataFusion SQL на batch, filter, rename, последовательные table rules; часть объединения совместимых таблиц. T5 |
| Выбор таблиц | Glob/regex Include/Exclude; MySQL уже принимает новые пустые CREATE TABLE через admission barrier. T4 |
| Parser errors и форматы | DLQ, JSON unknown-field policies, JSON/TSKV, Debezium, Avro/Protobuf Schema Registry; Parquet у S3. T9 |
| UI/API и диагностика | Draft/revision/CAS, validate/start/stop/logs, preview/schema viewer, подробные throughput/backpressure/CPU/RSS counters. T7 |
| Настройка производительности | Коннекторные performance options, изолированный Speedtest и поиск по разрешённым параметрам. T10 |
| Подсчёт результата | Точные output row counts и destination count reconciliation для поддержанных single-worker snapshots. Не checksum reconciliation. T8 |
| Extensibility / несколько endpoints | Typed registry и расширения; installation resolution может создавать несколько независимых source×sink pipelines. Не shared-read DAG. T5, T10 |

## Ранжированный список

### I. Наибольшая отдача для текущего ядра: № 1–16

| № | Чего не хватает | Сейчас в Transferia | Почему важно; у кого есть пример |
|---:|---|---|---|
| **1** | **Параллельный snapshot одной PG/MySQL-таблицы**: стабильные range/chunk boundaries, split key, ограничение readers, обработка skew | **Нет** для PG/MySQL: partition на целую таблицу, без range predicate. T1; не относится к уже распараллеленным OpenSearch/YT | Устраняет потолок одной большой таблицы. [SeaTunnel PG 2.3.13](https://seatunnel.apache.org/docs/2.3.13/connectors/source/PostgreSQL-CDC/) имеет split size/key и sampling для неравномерного распределения. Деление по нестабильному ключу требует отдельного consistency-контракта. |
| **2** | **Возобновление initial snapshot по завершённым чанкам**, без перечитывания всей таблицы/сброса destination | **Нет** у PG/MySQL batch-and-stream после потери snapshot owner: нужен явный reset. T3 | Критично для многочасовых загрузок. [Flink CDC PG 3.5](https://nightlies.apache.org/flink/flink-cdc-docs-release-3.5/docs/connectors/flink-sources/postgres-cdc/) поддерживает chunk checkpoints в incremental snapshot режиме; у PG он experimental. Нужны persisted split state и совместимый sink replay, не просто OFFSET. |
| **3** | **Контролируемая online schema evolution существующих таблиц**: ADD/расширение типа/rename и явная политика для несовместимых изменений | **Частично**: preflight/drift detection и new-table admission есть; drift существующей схемы в проверенных CDC путях останавливает поток. T4 | Обычная DDL не должна неизбежно превращаться в ручную пересборку pipeline. [Flink CDC policies](https://nightlies.apache.org/flink/flink-cdc-docs-release-3.5/docs/core-concept/schema-evolution/), [CData add/widen](https://cdn.cdata.com/help/ASN/sync/Features.html). Не копировать lossy `try_evolve`/silent casts; default — безопасный отказ. |
| **4** | **Source↔destination reconciliation по значениям**: checksums диапазонов, row diff, локализация и явный repair plan | **Частично**: output counts/ограниченная destination count check; совпадение counts не доказывает равенства значений. T8 | Находит незаметные пропуски, дубли и неправильные значения. [HVR 6 Compare](https://fivetran.com/docs/hvr6/getting-started/concepts/compare) предлагает checksum, row-wise и online compare. Для нас hash — фильтр, расхождения подтверждаются исходными значениями; repair только по согласию. |
| **5** | **Checkpoint-coupled transactional/idempotent SQL sink commit**: повтор после ambiguous write не создаёт второй эффект, в частности в append workloads | **Частично**: ordered commit barrier есть, но PG/MySQL/ClickHouse пути явно at-least-once; это не отсутствие guarantees у всех sinks. T8 | Основа безопасного автоматического recovery и resumable chunks. [SeaTunnel JDBC 2.3.13](https://seatunnel.apache.org/docs/2.3.13/connectors/sink/Jdbc/) имеет explicit `is_exactly_once` через XA только для поддерживающих его БД. Наш механизм может быть другим — atomic progress ledger/idempotent commit; он должен проверяться crash injection вокруг commit и не подменять business PK deduplication. |
| **6** | **Управляемый parallel CDC apply** после одного log reader: независимые ключи/таблицы, reorder/commit barriers | **Частично**: несколько partition actors есть, но PG/MySQL stream — одна source partition; нет общего dependency-aware apply scheduler. T6 и локальный runtime-аудит | Может убрать bottleneck записи без фиктивного «параллельного WAL». [HVR Integrate groups](https://fivetran.com/docs/hvr6/faq/how-to/multiple-integrate-jobs-running-simultaneously) требуют эксклюзивного распределения таблиц между jobs. [Striim writers, docs 5.4.0](https://www.striim.com/docs/en/creating-multiple-writer-instances--parallel-threads-.html) ограничивает generic DB parallel writers initial-load сценариями; recovery может отключать threads. Ни один пример не доказывает произвольный parallel apply с сохранением глобального transaction order. |
| **7** | **Online incremental snapshot/backfill во время CDC**: watermarks, конфликтующие READ/UPDATE/DELETE, bounded chunks | **Нет** такого режима у проверенных PG/MySQL: snapshot, затем stream, не DBLog. T3 | Добавление/перезагрузка большой таблицы без остановки live updates. [Debezium incremental snapshots](https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-incremental-snapshots). Это отдельная семантика от точного initial handoff и от timestamp polling. |
| **8** | **Автоматическое восстановление на другом worker/host и HA control plane** с fencing | **Частично**: local supervisor/CAS защищают lifecycle; restart сервера оставляет deliveries stopped. T6–T7 | [StreamSets failover](https://www.ibm.com/docs/en/streamsets-controlhub?topic=instances-data-collector-pipeline-failover) переносит job с last-saved offset, но требует пережить downtime на стороне source. [Striim failover](https://www.striim.com/docs/en/continuing-operation-after-server-failover.html) требует recovery и минимум двух servers; доступен Platform/Cloud Mission Critical, не Cloud Enterprise. Для Transferia обязательны ownership/fencing. |
| **9** | **Shared remote durable state backend**: offsets, phases, leases, recovery на другом host | **Частично**: порт `DurableStorage` уже есть, configured backend только LocalFile. T6 | Основа № 8 и distributed checkpoints; не самостоятельная гарантия exactly-once. [Debezium state storage](https://debezium.io/documentation/reference/3.7/configuration/storage.html) описывает альтернативные stores. Нужны CAS/lease semantics и проверка replay identity, а не просто загрузить JSON в S3. |
| **10** | **Online включение новых/ранее не выбранных таблиц с корректным bootstrap**, в том числе PostgreSQL | **Частично**: MySQL fresh CREATE TABLE поддержан; PG membership фиксирован, rename существующей MySQL-таблицы не backfill'ится. T4 | Wildcard subscription должна уметь безопасно развиваться. [Debezium ad-hoc snapshot signals](https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-ad-hoc-snapshots) дают выборочный snapshot. Не включать существующую таблицу с середины CDC без её истории. |
| **11** | **Операционная видимость freshness/CDC lag и SLA alerts**, а не только rec/s | **Частично**: есть source metadata, stats и logs; нет встроенного SLA/alert subsystem. T7 | Быстрый pipeline может незаметно отставать. [Striim LEE](https://www.striim.com/docs/platform/en/monitoring-end-to-end-lag--lee-.html) — sampled lag metric с короткой историей; [alerting](https://striim.com/docs/platform/en/alerting-in-striim.html) — отдельный механизм. Это не доказательство долговременного SLA ledger. Retention/WAL headroom нужно проверять отдельно. |
| **12** | **Rate shaping источника/destination**: rows/s, bytes/s, burst и scope per-delivery/table | **Частично**: memory backpressure и batch/concurrency limits есть; общего read-rate limit нет. T6–T8 | Ограничивает ущерб production-БД, не только RAM нашего процесса. [DataX speed controls](https://github.com/alibaba/DataX/blob/master/introduction.md) задают channel/byte/record limits. Общая квота и per-partition квота — разные вещи; burst/scopes — требования к нашему дизайну, не обещание всех этих настроек у DataX. |
| **13** | **Coordinated savepoint → inspect → restore/drain** как управляемая операция | **Частично**: connector checkpoints и stop/start есть; нет переносимого savepoint artifact и multi-worker barrier. T6–T7 | Обслуживание и обновления без ручного редактирования state. [SeaTunnel REST lifecycle](https://seatunnel.apache.org/docs/engines/zeta/rest-api-job-lifecycle/) документирует savepoint/recovery; эта неприкреплённая страница относится к текущей docs-линии, не обещание поддержки в каждом старом релизе. |
| **14** | **Authenticated multi-user control plane: SSO/API identity/RBAC** | **Частично** только local safety: loopback, private files, CAS; нет user/resource authorization. T7 | Обязательный барьер перед shared/network deployment. [Fivetran RBAC](https://fivetran.com/docs/using-fivetran/fivetran-dashboard/account-settings/role-based-access-control), [NiFi administration](https://nifi.apache.org/nifi-docs/administration-guide.html). Это расширение local-only продукта, не обвинение localhost-сервера в обходе заявленной модели. |
| **15** | **Spill больших незавершённых CDC-транзакций на диск** с recovery и лимитом диска | **Нет** общего механизма; MySQL держит bounded transaction buffer и явно отказывает при превышении настроенных limits | Позволяет обрабатывать большие legitimate transactions без увеличения RAM/разрыва atomicity. [HVR agent disk/spill](https://fivetran.com/docs/hvr6/install-and-upgrade/system-requirements/agent-disk-requirements), [capture checkpoints](https://fivetran.com/docs/hvr6/advanced-operations/tuning-capture-checkpoints). Основание у нас: [MySQL stream config](../crates/transferia-connector-mysql/src/connectors/mysql/src_stream/config.rs). Не подменять spill неявным дроблением транзакции. |
| **16** | **Параллельные S3 file/split readers с сохраняемым progress** | **Нет** в текущем S3 source: один logical partition, последовательные objects/active Parquet stream, commit_offsets no-op. T9 | Большой набор файлов упирается в serial extraction. [SeaTunnel S3File 2.3.13](https://seatunnel.apache.org/docs/2.3.13/connectors/source/S3File/) документирует parallelism и snapshot прочитанных splits; [LocalFile](https://seatunnel.apache.org/docs/2.3.13/connectors/source/LocalFile/) отдельно описывает large-file splitting. Parquet row-group splitting — следующий уровень, его не нужно приписывать любому file connector. Нужны stable object/version checks; concurrent S3 uploads у нас уже есть. |

### II. Полноценные integration pipelines и ежедневная эксплуатация: № 17–36

| № | Чего не хватает | Сейчас в Transferia | Польза и официальный пример |
|---:|---|---|---|
| **17** | **Пользовательский source-side query/projection/filter pushdown** для batch extraction | **Частично**: типовые projection/casts есть, DataFusion фильтрует уже прочитанный batch; у PG/MySQL нет пользовательского WHERE/query в source contract. T1, T5 | Не передавать ненужные строки/колонки по сети. [Flink PG snapshot statement overrides](https://nightlies.apache.org/flink/flink-cdc-docs-release-3.5/docs/connectors/flink-sources/postgres-cdc/) применяются только к snapshot — stream filter требует отдельной согласованной семантики. |
| **18** | **Incremental SQL extraction по update-key/bookmark** без WAL/binlog | **Нет** готового режима в проверенных SQL sources; log-based CDC не заменяет его. T1, T10 | Интеграции без replication privileges, периодические выгрузки. [Sling incremental/backfill modes](https://docs.slingdata.io/concepts/replication/modes), [CData incremental columns](https://www.cdata.com/kb/entries/sync-incremental-config.rst). Нужны tie-breaker/overlap; timestamp polling само по себе не ловит deletes. |
| **19** | **Durable schedules и повторные интервальные runs**: cron/timezone/missed-run policy, зависимости окон, retries | **Частично**: ручной lifecycle и logs есть, scheduler/run ledger нет. T7 | Batch ETL должен повторяться без набора внешних скриптов. [ADF tumbling windows](https://learn.microsoft.com/en-us/azure/data-factory/how-to-create-tumbling-window-trigger). Окно — orchestration state, не DB transaction. |
| **20** | **Управление отдельной таблицей:** resync с диагностикой влияния; независимая пауза/диапазонный backfill где это допустимо | **Частично**: rules выбирают таблицы, но lifecycle delivery-level. T4, T7 | Не перезапускать здоровую часть большой интеграции. [Fivetran table-level re-sync](https://fivetran.com/docs/connectors/troubleshooting/trigger-historical-re-syncs) подтверждает выборочную перезагрузку; [Sling backfill](https://docs.slingdata.io/concepts/replication/modes) — диапазонную загрузку. Это не универсальная pause/resume гарантия для произвольного CDC: изоляция таблиц не должна нарушать cross-table transactions. |
| **21** | **TRUNCATE как отдельное CDC-событие и явное destination действие** | **Нет** у PG decoder; событие отвергается, не превращается молча в deletes. T4 | Частый сценарий staging/refresh таблиц. [Debezium PG truncate events](https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-truncate-events). Возможность зависит от destination; порядок относительно DML нельзя угадывать. |
| **22** | **Версионированная schema history, привязанная к log position**, для replay через DDL | **Частично**: authoritative schema identity и drift rejection есть; нет общего DDL-history replay. T3–T4 | Не декодировать старые события новой схемой. [Debezium MySQL schema history](https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-schema-history). Дополняет № 3: применить новый DDL и корректно пережить restart через него — разные задачи. |
| **23** | **Shared-read fan-out в несколько sinks с ack от всех обязательных ветвей** | **Нет** DAG такого вида; installation expansion создаёт независимые pipelines. T5 | Одна дорогая extraction для DWH+архива+очереди. [Conduit pipeline semantics](https://conduit.io/docs/core-concepts/pipeline-semantics/). Это не distributed atomic commit всех sinks: политика partial success/replay должна быть явной. |
| **24** | **Контентная маршрутизация и ветвление**, разные transforms/sinks по row/header predicates | **Частично**: per-table Include/Exclude и parser table naming есть; arbitrary branch graph нет. T5, T9 | Обогащение и раздельная доставка классов данных без дублирования source reads. [Redpanda switch](https://docs.redpanda.com/connect/components/processors/switch/), [Bento workflow](https://warpstreamlabs.github.io/bento/docs/components/processors/workflow/). Требуются default/error routes и видимый ack contract. |
| **25** | **Stateful joins нескольких streams/tables** | **Нет** maintained multi-input join; DataFusion видит один batch `input`. T5 | Собрать orders+customers, изменения справочника и фактов. [Estuary derivations](https://docs.estuary.dev/concepts/derivations/) хранят state между сообщениями. Batch-local/self-join SQL не равен восстанавливаемому stream join. |
| **26** | **Cross-batch aggregations и streaming windows** с state/recovery/late-event semantics | **Нет**; SQL aggregate сейчас ограничен отдельным batch. T5 | Непрерывные счётчики и агрегаты независимо от размера source batch. [Estuary stateful derivations](https://docs.estuary.dev/concepts/derivations/). Count/byte batching у sinks не заменяет event-time windows; конкретный watermark/late policy нужно проектировать отдельно. |
| **27** | **Непрерывный file/object ingestion**: обнаружение новых объектов, persisted cursor/manifest, duplicate/version handling | **Нет** у S3 source: finite listing/read, не watch/subscription. T9 | Новые файлы должны поступать без полной повторной выгрузки prefix. [Redpanda aws_s3 input](https://docs.redpanda.com/connect/components/inputs/aws_s3/) использует polling/notifications-сценарии; проверять выбранный режим. Нельзя считать ETag универсальным content hash или заменять изменившийся объект молча. |
| **28** | **Durable disk spool между capture и delivery** для длительной недоступности sink | **Частично**: memory backpressure и commit state есть; generic persisted payload queue нет. T6, T8 | Снижает зависимость от upstream retention, позволяет пережить outage в пределах диска. [InLong DataProxy disk channel](https://inlong.apache.org/docs/1.10.0/modules/dataproxy/overview). Не то же самое, что state-файл, и не разрешение ACK до согласованного durable barrier. |
| **29** | **Переиспользуемые named credentials и secret lifecycle**: external provider, scoped access, rotation/lease handling | **Частично**: token files, inline credentials, redaction/installation resolution есть; общего server-side secret registry нет в проверенной композиции. T7, T10 | Убрать копии секретов из множества drafts, управлять истечением/ротацией. [ADF security/Key Vault](https://learn.microsoft.com/en-us/azure/data-factory/secure-your-azure-data-factory). Browser password helpers не являются secret manager backend. |
| **30** | **Durable audit trail действий оператора/API**: actor, diff, reason, run/config identity | **Нет** модели actor/audit events; current revision и worker logs — другое. T7 | Разбирать кто изменил production delivery и воспроизводить инцидент. [StreamSets audits](https://www.ibm.com/docs/en/streamsets-controlhub?topic=manage-audits), [Fivetran logs/audit](https://fivetran.com/docs/logs). У Fivetran Audit Trail ограничен старшими планами. |
| **31** | **Native metrics exporters и исторические dashboards по run/stage/table** | **Частично**: сильные structured console stats; встроенного exporter/time-series subsystem в inspected config/API нет. T7 | Интеграция с мониторингом без парсинга строк и сопоставление нескольких runs. [Bento monitoring](https://warpstreamlabs.github.io/bento/docs/guides/monitoring/). Внешний агент сбора логов может закрыть часть потребности; это не отсутствие метрик как таковых. |
| **32** | **Операционный quarantine/DLQ workflow** для transform/data-quality failures: просмотр, исправление, выборочный безопасный replay | **Частично**: parser DLQ с исходным payload уже есть; общего exception graph и replay console нет. T5, T7, T9 | Ошибки становятся управляемой очередью работы. [Bento error handling](https://warpstreamlabs.github.io/bento/docs/configuration/error_handling/), [NiFi provenance/replay](https://nifi.apache.org/nifi-docs/user-guide.html). Не направлять в DLQ ambiguous sink commits: это не обычная плохая строка. |
| **33** | **Пользовательские data-quality assertions** с диагностикой и метриками качества | **Частично**: schema/PK/type validation и SQL filter есть; catalog бизнес-правил и отчёт invalid business rows отсутствуют. T5, T8 | Например, бизнес-диапазоны или referential checks, а не молчаливый WHERE. [Qlik validation rules](https://help.qlik.com/en-US/cloud-services/Subsystems/Hub/Content/Sense_Hub/DataIntegration/DataProducts/Working-with-validation-rules.htm) подтверждает assertions/quality scoring, но не общий quarantine/replay. Reject/quarantine — отдельная интеграция с № 32. Не все проверки streaming/local; общая уникальность требует state. |
| **34** | **Явный SCD2/history/soft-delete режим materialization** | **Частично**: CDC operation-aware writers и Debezium envelope есть; ready-made temporal table contract нет. T8–T10 | Хранить историю как выбранный продуктовый режим, не случайные дубли. [Fivetran History Mode](https://fivetran.com/docs/core-concepts/sync-modes/history-mode). Не менять default «одна текущая строка на PK»; CDC JSON archive сам по себе не SCD2. |
| **35** | **Staged full refresh SQL destination**: временная таблица, проверка, controlled final load; atomic publish где БД это допускает | **Частично**: отдельные sinks имеют свои replace/commit механизмы; общей SQL refresh policy нет. T8 | Изолировать подготовку новой версии данных от рабочей таблицы. [Sling modes](https://docs.slingdata.io/concepts/replication/modes) подтверждает temporary-table staging, но не универсальный atomic swap. Reader isolation/atomic publish — отдельный желаемый контракт с ограничениями конкретной БД/DDL/constraints. |
| **36** | **Elastic rescale/rebalance без полного stop/rebootstrap** | **Частично**: fixed worker assignment и broker lanes есть; generic live repartition/state transfer нет. T6 | Увеличивать/уменьшать ресурсы по нагрузке. [Estuary task shards](https://docs.estuary.dev/concepts/advanced/shards/) описывает no-downtime splits; там split выполняет service operator, не обязательно автоматическое autoscaling. |

### III. Расширение ETL-сценариев и зрелость платформы: № 37–53

| № | Чего не хватает | Сейчас в Transferia | Польза и официальный пример |
|---:|---|---|---|
| **37** | **External lookup/enrichment**: parameterized SQL/API request, request/result mapping, cache/TTL, bounded concurrency | **Нет** готового middleware для lookup; DataFusion выполняет SQL над локальным `input`, а не подключённым справочником. T5, T10 | Добавить информацию из справочника без полноценного multi-stream join. [Bento SQL select](https://warpstreamlabs.github.io/bento/docs/components/processors/sql_select/), [cached enrichment](https://warpstreamlabs.github.io/bento/docs/components/processors/cached/). Для повторяемости нужны явные freshness, timeout, missing-key и replay semantics. |
| **38** | **Retained capture journal для rebuild downstream без повторного чтения источника** | **Нет** встроенной replayable collection/history; можно отдельно писать в queue/S3, но это самостоятельная pipeline. T5–T6, T8 | Пересчитать новую трансформацию или новый sink на сохранённой истории. [Estuary journals](https://docs.estuary.dev/concepts/advanced/journals/) хранят историю в object storage с чтением по offsets. Отличие от № 28: spool освобождается после доставки, journal сохраняется по явной retention policy. |
| **39** | **Dependency-aware ELT jobs после загрузки**: warehouse SQL/dbt, зависимости нескольких inputs, tests и failure propagation | **Нет** first-class ELT workflow; middleware работает в процессе переноса. T5, T7 | Завершить цепочку «ingest → модели → checks → публикация». [Fivetran dbt transformations](https://fivetran.com/docs/transformations/dbt). Не обязательно встраивать dbt: можно дать проверяемый orchestration port к внешнему исполнителю. |
| **40** | **История конфигураций, diff, promotion dev→prod и контролируемый возврат версии** | **Частично**: current revision/CAS и JSON/YAML есть; revision не является архивом старых версий. T7 | Воспроизводить запуск и безопасно выпускать изменения. [StreamSets version history](https://www.ibm.com/docs/en/streamsets-controlhub?topic=pipelines-overview), [Qlik validated import](https://help.qlik.com/en-US/cloud-services/Subsystems/Hub/Content/Sense_Hub/DataIntegration/DeclarativePipelines/Deploying-pipeline-configuration.htm). Возврат config не откатывает destination DDL/data: совместимость checkpoint нужна отдельно. |
| **41** | **Переиспользуемые parameterized templates/subflows и environments** с типизированными run parameters | **Частично**: installation resolver уже умеет выбирать deployments/endpoints; general workflow templates/parameter scopes нет. T5, T10 | Поддерживать много однотипных deliveries без копирования конфигов. [Hop variables/parameters](https://hop.apache.org/manual/latest/variables.html), [projects/environments](https://hop.apache.org/manual/latest/projects/index.html). Параметры не должны обходить preflight или подменять идентификаторы неявно. |
| **42** | **Пользовательские golden tests для конкретной pipeline**: входные fixtures, expected rows/schema, test-before-activate | **Частично**: developer unit/E2E tests, validate и preview есть; user-owned test-suite resource нет. T5, T7 | Ловить изменение бизнес-результата при редактировании SQL/rename, не только валидность конфигурации. [Estuary catalog tests](https://docs.estuary.dev/concepts/tests/) задают ingest/verify fixtures. Это не замена real-wire E2E самого продукта. |
| **43** | **Явная бизнес-дедупликация / conflict-resolution materialization** с key, order/tie-breaker, state и delete semantics | **Частично**: PK identity, replay safety и CDC apply есть; выбираемой cross-batch политики разрешения конфликтующих бизнес-записей нет. T5, T8 | Для feeds с несколькими версиями записи или нескольких источников. [dlt merge/dedup_sort](https://dlthub.com/docs/general-usage/merge-loading). Не копировать arbitrary winner по умолчанию: стандартный режим Transferia должен продолжать отвергать неоднозначные дубли. |
| **44** | **Дополнительные file parsers/writers**: CSV с quoting/encoding, XML, ORC; отдельно Avro container files | **Частично**: S3 JSON/Parquet/discard и MQ JSON/TSKV/Schema Registry уже есть. T9 | Расширить файловый ETL без внешней конвертации. [SeaTunnel LocalFile formats](https://seatunnel.apache.org/docs/2.3.13/connectors/sink/LocalFile/) подтверждает CSV/XML/ORC; [NiFi AvroReader](https://nifi.apache.org/components/org.apache.nifi.avro.AvroReader/) читает embedded-schema Avro, не только Confluent-wire. Не обещать одинаковые типы/режимы чтения и записи для всех форматов. |
| **45** | **Декларативный framework API extraction**: pagination, child endpoints, incremental cursor, auth/retry/rate limit; генерация reviewable config | **Нет** такого user-facing source framework в built-in catalog; общий безопасный HTTP transport уже существует. T10 | Новый SaaS extractor не должен каждый раз заново реализовывать pagination и cursor bookkeeping. [dlt REST source](https://dlthub.com/docs/dlt-ecosystem/verified-sources/rest_api/basic), [OpenAPI generator](https://dlthub.com/docs/dlt-ecosystem/verified-sources/openapi-generator). Автогенерация не доказывает корректность API semantics; ссылки pagination также должны проходить outbound security boundary. |
| **46** | **Независимо поставляемые connector/plugin packages**: discovery/install и versioned metadata | **Частично**: typed Rust registry, compile-time extensions и fingerprint есть; общего external plugin package lifecycle нет. T10 | Обновлять интеграцию отдельно от всего бинаря. [Meltano plugins](https://docs.meltano.com/concepts/plugins) подтверждает installation и lock artifacts для discoverable plugins, но не custom/inherited plugins и не универсальную ABI-совместимость. Нашему дизайну дополнительно нужны version pinning/compatibility checks; plugin ABI имеет цену, нативный hot path предпочтителен. |
| **47** | **Record-level provenance и lineage с управляемым replay**: какие processors/config versions затронули запись | **Частично**: source metadata, logs и schema view есть; searchable provenance/event graph не предусмотрен проверенными CP/API/log contracts. T5, T7 | Объяснять происхождение конкретного результата, оценивать влияние изменения. [NiFi provenance](https://nifi.apache.org/nifi-docs/user-guide.html) связывает историю FlowFile с replay. Content retention, доступ к персональным данным и повторные side effects требуют отдельных ограничений. |
| **48** | **Projects/workspaces и resource pools/quotas для нескольких пользователей/команд** | **Нет** multi-tenant boundary в local single-user CP; per-delivery resource limits не заменяют общую изоляцию. T6–T7 | Не дать одному job занять весь общий worker pool. [StreamSets organization administration](https://www.ibm.com/docs/en/streamsets-controlhub?topic=manage-organization-administration), [Striim resource policies](https://www.striim.com/docs/en/resource-usage-policies.html). Имеет смысл после решения запускать Transferia как общий сервис. |
| **49** | **Декларативные field privacy controls**: allow/block/hash/mask с явной политикой и audit | **Частично**: SQL может убрать/преобразовать колонку; отдельного privacy policy catalog нет. T5, T7 | Сделать обработку чувствительных полей явно видимой оператору. [Fivetran blocking/hashing](https://fivetran.com/docs/core-concepts/features/data-blocking-column-hashing) подтверждает column blocking/hash, не универсальный reusable policy engine. Это намеренная трансформация по запросу, никогда не автоматическое «исправление» или lossless default. |
| **50** | **Relational normalization nested JSON** в связанные parent/child datasets | **Нет** готовой multi-dataset normalization с жизненным циклом дочерних строк; отдельные JSON paths/SQL transformations есть. T5, T9 | Грузить API documents в реляционную модель без ручной сборки всех child pipelines. [dlt normalizers/nested references](https://dlthub.com/docs/general-usage/schema). Нужны явные naming/key/update/delete policies; dlt default coercion/renaming переносить в Transferia нельзя. |
| **51** | **User-authored scripted transformations/UDF packages без пересборки Transferia** | **Частично**: SQL и compiled Rust middleware есть; runtime script/UDF catalog не предусмотрен проверенной built-in registry/runtime композицией. T5, T10 | Покрыть бизнес-логику, неудобную для SQL. [Estuary derivations](https://docs.estuary.dev/concepts/derivations/) поддерживают TypeScript; Python ограничен private/BYOC deployment. Sandbox, resource budget и воспроизводимость обязательны; производительность нужно измерять. |
| **52** | **Операторское inspect/reset/seek offsets API** с preview последствий, fencing и audit | **Частично**: durable offsets и connector-specific start modes есть; общей безопасной операции CP нет. T6–T7 | Управляемый replay выбранного диапазона вместо редактирования state-файла. [Kafka Connect offsets API](https://kafka.apache.org/36/kafka-connect/user-guide/) разрешает изменение offsets только stopped connector. В Transferia нельзя разрешать произвольный seek поверх несовместимого destination state. |
| **53** | **Bidirectional/active-active replication** с loop prevention и explicit conflict contract | **Нет** согласованного двунаправленного режима; две противоположные deliveries его не создают. T5, T8 | Расширенный, низкоприоритетный относительно one-way ETL сценарий. [HVR 6 bidirectional capabilities](https://fivetran.com/docs/hvr6/capabilities/615), [CollisionDetect](https://fivetran.com/docs/hvr6/action-reference/collisiondetect). Поддержка ограничена СУБД/версиями. Default HVR conflict winner не соответствует нашему fail-closed default — не копировать его неявно. |

## Недостающие коннекторы — отдельно от функциональных пробелов

Основание отсутствия — **встроенный каталог T10**, а не отсутствие совместимого протокола. Ниже приоритет для универсального database/queue/file ETL; это не утверждение о спросе конкретных пользователей. Направления в примерах указаны специально: наличие source не означает наличие sink, batch не означает CDC.

| Очерёдность | Семейство отсутствующих native integrations | Примеры и официальное подтверждение |
|---:|---|---|
| 1 | **SQL Server, Oracle, MongoDB, Db2** | SeaTunnel перечисляет SQL Server/Oracle/MongoDB batch и CDC sources; Db2 — JDBC source. [Sources 2.3.13](https://seatunnel.apache.org/docs/2.3.13/connectors/source/). Режимы CDC и поддержанные версии нужно оценивать по каждой СУБД отдельно. |
| 2 | **Snowflake, BigQuery, Redshift, Databricks/Delta Lake** | Snowflake/Redshift есть в [SeaTunnel sink catalog](https://seatunnel.apache.org/docs/2.3.13/connectors/sink/); BigQuery, Databricks, Delta — в [dlt destinations](https://dlthub.com/docs/dlt-ecosystem/destinations). Это прежде всего направление DWH/lakehouse sinks. |
| 3 | **Generic SQL/JDBC-class integration** и отдельные **Greenplum, DuckDB, Vertica, Doris, StarRocks** | [SeaTunnel JDBC/source catalog](https://seatunnel.apache.org/docs/2.3.13/connectors/source/) и [sinks](https://seatunnel.apache.org/docs/2.3.13/connectors/sink/). JDBC — пример чужого extensibility surface, не рекомендация тащить JVM в Rust runtime; native adapters предпочтительнее. |
| 4 | **HTTP/REST, GraphQL и SaaS extractors**: Salesforce, HubSpot, Stripe, Shopify, GitHub, Google Ads, Jira, Google Sheets | [dlt sources](https://dlthub.com/docs/dlt-ecosystem/verified-sources), [SeaTunnel sources](https://seatunnel.apache.org/docs/2.3.13/connectors/source/). № 45 — общий extraction framework; здесь именно готовые endpoints/API-specific contracts. |
| 5 | **Pulsar, RabbitMQ, RocketMQ, Amazon SQS**, затем **Kinesis, NATS, MQTT** | Первые четыре перечислены в [SeaTunnel sources](https://seatunnel.apache.org/docs/2.3.13/connectors/source/) / [sinks](https://seatunnel.apache.org/docs/2.3.13/connectors/sink/); остальные — в [Redpanda component catalog](https://docs.redpanda.com/connect/components/about/). Consumer acknowledgement и retention semantics разные, не просто смена URL Kafka. |
| 6 | **Local files, FTP/SFTP, HDFS/Hive; GCS, Azure Blob/ADLS** | Файловые/Hadoop endpoints — [SeaTunnel catalog](https://seatunnel.apache.org/docs/2.3.13/connectors/source/); cloud/filesystem destinations — [dlt destinations](https://dlthub.com/docs/dlt-ecosystem/destinations). Форматы выделены в № 44, чтобы не считать каждый формат отдельным connector. |
| 7 | **Hudi, Paimon**, отдельные lakehouse/catalog integrations | [SeaTunnel sinks](https://seatunnel.apache.org/docs/2.3.13/connectors/sink/) включает оба. Iceberg в Transferia уже есть, поэтому не попадает в этот список. |
| 8 | **Redis, Cassandra, DynamoDB, HBase, Kudu, Elasticsearch** | [SeaTunnel sources](https://seatunnel.apache.org/docs/2.3.13/connectors/source/) и [sinks](https://seatunnel.apache.org/docs/2.3.13/connectors/sink/). Elasticsearch здесь — native/version-tested support; наличие OpenSearch не доказывает совместимость с любой Elastic version. |
| 9 | **Специализированные graph/time-series/vector endpoints:** Neo4j, InfluxDB, IoTDB, Milvus, Qdrant | Есть в [SeaTunnel source](https://seatunnel.apache.org/docs/2.3.13/connectors/source/) / [sink](https://seatunnel.apache.org/docs/2.3.13/connectors/sink/) catalogs. Низкий приоритет без подтверждённого сценария. |

Не считаю новыми коннекторами MinIO/другой S3-compatible endpoint, Kafka-compatible Redpanda, ещё один hosted PostgreSQL или MySQL-compatible сервер только из-за бренда. Совместимость и особые CDC modes всё равно требуют отдельного подтверждения. Использование HDFS transport внутри Iceberg также не означает наличие универсального HDFS file source.

## Что делать первым: практический порядок с зависимостями

**Волна 1 — большие и прерываемые загрузки:** № 1 → № 2, с общей моделью split/checkpoint, затем № 16. Подготовить № 4 как независимый контроль результата, № 5 — как обязательный replay-контракт для выбранных SQL destinations. Для PG/MySQL выбрать и документировать consistency protocol до обещания resumability: потерянный connection-owned snapshot нельзя восстановить сохранённым номером чанка.

Chunked incremental snapshot с последующим согласованием через CDC **не тождествен одному прежнему MVCC snapshot на фиксированный момент**. Сравнивать и проектировать нужно гарантии наблюдаемого результата, а не только наличие кнопки resume; для snapshot-only режима без журнала возможны другие ограничения.

Минимальные критерии готовности:

- Одна таблица реально читается несколькими workers/ranges, а не только формируется несколько Arrow batches.
- Покрыты empty table, skew, gaps, composite/nullable key policy, concurrent INSERT/UPDATE/DELETE и изменение split key.
- Kill/restart в середине chunk/commit не даёт пропусков или неоднозначных PK; повторяется ограниченный объём, а не вся таблица.
- Source load и memory bounded; concurrency — явная настройка. Throughput и overhead измерены, обещания ускорения заранее не даются.

**Волна 2 — долго живущий CDC:** № 3 + № 22, № 7 + № 10, затем № 6 и № 15. Сначала зафиксировать ordering/transaction/DDL barriers. Критерий: source commit никогда не обгоняет долговечное применение обязательных зависимостей; несовместимая DDL останавливается до side effects; replay использует нужную версию схемы.

**Волна 3 — эксплуатация:** № 9 → № 8, № 11–13, № 19–20, № 29–31, № 40–42. Для общего сервиса № 14, № 29–30, № 48 — prerequisite, а не необязательный финальный polish. Проверка HA должна включать network partition и fencing прежнего owner, а не только обычный restart.

**Волна 4 — расширение ETL:** № 23–26, № 32–39, № 43–51 по реальному спросу. Не вводить stateful DAG или plugin ABI только ради feature parity: это заметно меняет модель продукта. № 53 — самостоятельное решение о позиционировании, а не естественный следующий шаг после one-way replication.

Это порядок зависимостей, поэтому он не обязан буквально повторять рейтинг ценности. Оценки трудоёмкости и календарные сроки не давались: для них потребуется отдельный design/prototype этап.

### Ограничения выводов

- Это исследование документации и кода, **не сравнительный benchmark**. Оно не доказывает, что конкурент быстрее или надёжнее Transferia.
- Отсутствие относится к указанному local checkout и встроенной композиции; состояние удалённого deployment, внешние runbooks и непроверенные закрытые расширения не предполагаются.
- Нельзя доказать абсолютную полноту «всех возможностей всех ETL». Корпус ограничен 22 выбранными продуктами/семействами; источники, пробелы и оставшиеся ограничения перечислены явно.
- Living docs и страницы `latest`/`next` могут измениться. Версионированные ссылки использованы там, где доступны; сторонние roadmap promises не принимаются за shipped capability.
- Generic retries, memory backpressure, validation, previews, filters/SQL, schema registry, multi-table delivery, tuning, row counts и commit state исключены как уже существующие. Запрос «exactly-once везде» не включён: гарантии необходимо сравнивать по конкретной source/sink pair и модели сбоя.
- Не рекомендовано копировать чужие lossy defaults: arbitrary dedup, auto-renaming, narrowing/coercion, unacknowledged drops, conflict last-write-wins и destructive re-sync. Новые функции должны сохранять явный контракт и fail-closed default Transferia.
- Производственный код не изменялся; компиляция, тесты и новые benchmark runs для этого отчёта не нужны и не запускались.
